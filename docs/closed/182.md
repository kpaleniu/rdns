### 182. Catalog zones are consumed, never generated — **filed 2026-10-05, closed 2026-10-07**, **enhancement**

`docs/spec/03` §3.10 says the producer side "needs no code — a catalog is an
ordinary zone". True for BIND, which also only consumes. Knot generates a
catalog from its configuration (`catalog-role: generate`, 3.1.0) and PowerDNS
Auth is producer and consumer (4.7.0): add a zone on the primary and the
secondaries provision it with no second edit.

Here the operator keeps the zone list and the catalog's member records in
step by hand, which is the drift `CLAUDE.md` §7 is about, across two files.

> *This was generated by AI during triage.*

**Triaged 2026-10-06: enhancement, ready-for-agent.** Term in `CONTEXT.md`:
**Generated catalog**.

**Category:** enhancement
**Summary:** `rdnsd` builds an RFC 9432 catalog zone from the zones it is
primary for, so a zone file dropped into `--zone-dir` is provisioned on every
consuming secondary with no second edit.

**Current behavior:** the consumer side is complete (`docs/spec/03` §3.10).
A producer's catalog must be written by hand, beside the zone files it lists.

**What RFC 9432 asks of a producer**, quoted:

- §4.1: each member is `<unique-N>.zones.$CATZ PTR member.`; the PTR "MUST be
  the only record in the PTR RRset", and two labels naming one member make
  the catalog broken.
- §5.4 with §5.6: a member whose label changes is processed by consumers as
  a removal and an addition, with its state reset. Labels must be stable.
- §6: "a catalog producer MUST NOT use names that are not under the control
  of the catalog producer (with the exception of reserved names)", with
  `invalid.` RECOMMENDED; operators "SHOULD limit the systems able to query
  these zones"; and the empty-catalog failure that takes every member off
  every secondary "within seconds".

**Desired behavior:**

- `--generate-catalog NAME`, or `generate-catalog` in `[server]`; one per
  server. `NAME` must be at or under `invalid.`, or strictly under a zone this
  server is primary for (§6's MUST, as far as the code can check). Refused
  otherwise at startup, before `--check-config` returns.
- Members: every zone this server is primary for, except the catalog itself
  and any zone whose `[zones.*]` table says `catalog = false`. Secondary
  zones are never members. Opt-out rather than Knot's and PowerDNS's opt-in,
  because zones arrive here as files with no configuration entry.
- Member labels: the first 16 hex characters of SHA-256 over the member's
  lowercased wire-format name. Stable across restarts and regenerations with
  no state file. A collision between two members is a refused generation,
  never a published broken catalog.
- Contents: SOA, `NS invalid.`, `version.$CATZ TXT "2"`, one PTR per member.
  No `group`, `coo` or `*.ext` properties.
- Serial: moves on every membership change, through the serial machinery
  re-signing already uses, and only then.
- Regenerated after each reload, from the same all-or-nothing load (§4): an
  unreadable `--zone-dir` fails the reload, it does not publish an empty
  catalog. Each member removed is logged at WARN with its name.
- Served by transfer only, under the existing transfer ACL and per-key zone
  scoping (#16), with NOTIFY to `also-notify` targets on every change.
  Ordinary queries for names at or under it are REFUSED.
- Consuming the catalog this server generates is refused at startup.
  Consuming other catalogs while generating one is allowed.
- `docs/spec/03` §3.10 gains the producer side; its struck "needs no code"
  line already points here.

**Acceptance criteria:**

- [ ] Three zone files in `--zone-dir`: the generated catalog, read back by
      `rdns::catalog::Catalog::from_zone`, lists exactly those three.
- [ ] A fourth file plus a reload: four members, serial moved, the first
      three labels unchanged; NOTIFY sent.
- [ ] Reload with nothing changed: serial unchanged.
- [ ] `catalog = false` on one zone leaves it out.
- [ ] Labels are identical across a restart (compare two runs).
- [ ] Deleting a file: one fewer member, a WARN naming it.
- [ ] An unreadable `--zone-dir` on reload: the reload fails and the
      catalog keeps its members.
- [ ] End to end: a second `rdnsd` consuming the catalog provisions all
      members, and a newly added zone, with no edit on its side.
- [ ] AXFR of the catalog is allowed only as the transfer ACL allows; an
      ordinary query for `version.$CATZ` is REFUSED.
- [ ] Startup refuses a name outside `invalid.` and outside every primary
      zone, and consuming our own catalog, also under `--check-config`.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit.

**Out of scope:**

- `group`, `coo` and custom properties in the generated catalog.
- More than one generated catalog per server.
- Including secondary zones as members.

Where this differs from the brief, and why:

- **The opt-out is `catalog-member = false`, not `catalog = false`.**
  `[zones.*] catalog` already means "consume this zone as a catalog", and
  defaults to false. Reusing it would have left out every zone that has a
  table at all.
- **The serial is Unix seconds, not `signed_serial`.** `signed_serial`
  counts hours, so two membership changes within one hour would share a
  serial, and a consumer that had seen the first change would never fetch
  the second. When the clock is not ahead of the last serial, it goes up by
  one instead.
- **The apex SOA is answered to a peer that may transfer the catalog.** That
  is a consumer's refresh query, and refusing it stops refreshes.
  Everything else under the catalog is REFUSED.
- **The catalog is not signed.** It is built after signing, and no
  consumer needs DNSSEC on it: the transfer ACL and TSIG authenticate it.
