### 151. The chain-of-trust walk has no type, so its RFC rules live in the async loop — **filed 2026-10-01, closed 2026-10-03**, **bug** since 151a

`dnssec_chain` publishes 26 items (`pub (fn|struct|enum|const|type|trait)`
above its tests). Outside `rdns` two are named, `ValidationState` and
`TrustAnchors`; inside, `rfc5011` names `TrustAnchors` and every other
driver of the validator is `rdns/src/resolver/validate.rs`. `ChainValidator`,
`KeyStore`, `DelegationEvidence`, `DelegationVerdict`, `RecordsVerdict`,
`WildcardExpansion`, `ChainShape` and `cname_chain_shape` appear in no `pub`
signature of `Resolver`.

The module's header gives the reason for the shape: "Synchronous: the records
are arguments, because fetching them is the resolver's job. The resolver
drives the loop and calls in at each step." That keeps the I/O out, and also
keeps the loop out. `establish_chain` (`validate.rs:142`) holds both: the
fetch, the key cache and `next_cut_below` are I/O; the anchor start, the
resume depth, the `label_count() + 2` step cap and the `DelegationVerdict`
transitions are RFC 4035 §5 and reach a test only through the resolver.

A rule written twice, with the comment saying so (`validate.rs:155`):
"Resume as deep as already trusted, by the same rule `best_start` used…
Disagreeing makes the walk skip a zone cut". They are different predicates.
`best_start` (`recurse.rs:209`) takes the deepest ancestor with a live
delegation entry *and* held keys; `establish_chain` takes the deepest under
the anchor with held keys alone. The weaker test resumes at least as deep,
which is the safe direction while both read the same cache state. Not
checked: a key entry (`MAX_KEY_TTL` 86 400, `resolver/caches.rs:237`)
expiring between `best_start` and `establish_chain`, which resumes the walk
*above* where the resolution started, with no referral evidence for the cut
in between.

A shape with no I/O in it would be a walker the resolver feeds — asks for a
zone's DNSKEYs or the cut below a zone, is handed them, ends in a
`ValidationState`. Not built; §19 says to build it before choosing it, and it
has one caller, so what it would buy is the test surface and one home for the
resume rule, not substitution.

**A second window, found reading for triage.** `KeyCache::holds` is
`get().is_some()`: it reads the keys and drops them. `establish_chain`
chooses its resume zone with `holds` and then calls `get` for the same zone
at the top of the loop; an entry expiring between the two reads sends the
loop to fetch and validate the DNSKEYs against `ds_set = Vec::new()`, which
the resume step emptied because "the DS that got us there is not needed
again". Both windows read as failing closed — Bogus, so SERVFAIL, for a
secure answer, never a false Secure — which is reasoning, not a result.

Rejected on the way: walking from the anchor every time, because the
referrals above a deep start were never seen and `next_cut_below` has no
evidence for those cuts; one predicate shared by both sites, which removes
the duplicate rule and keeps two reads at two instants; an async walk generic
over a source trait, which breaks the module's "Synchronous" header and would
have one implementation. Q2 kept the walk to the chain for one target:
`validate`'s top half — signers, negativity, shape, wildcard proofs — is out.

#### Agent brief — 151a

**Category:** bug, if it reproduces
**Summary:** Show whether a key-cache entry expiring mid-resolution turns a
secure answer Bogus.

**Current behavior:** the resolution's start is chosen by one predicate
(`best_start`: a live delegation and held keys) and validation's resume by
another (`establish_chain`: held keys under the anchor), each reading
`KeyCache` at its own instant; inside `establish_chain`, `holds` and `get`
read it twice more.

**Desired behavior:** two resolver tests, through the exchange seam (#136)
with `Clock::Fixed`, each answering a signed question whose zone's keys are
cached at the start:
1. the clock advances past the key entry's expiry between the start being
   chosen and the walk running;
2. the clock advances past it between the resume choice and the first key
   lookup.

Each asserts the answer validates `Secure`. If either fails, it is kept as
the regression test for 151c and the row is relabelled **bug**; if neither
can be made to fail, the row says so and why.

**Acceptance criteria:**
- [ ] Both tests exist and their outcome against the current code is
      recorded in this row, with the `ValidationState` each produced.
- [ ] A test that fails is not fixed here.

**Out of scope:** the fix (151c); any change to cache TTLs or capacities.

**Result, 2026-10-02.**

- **The first window reproduces.**
  `resolver::tests::a_key_set_expiring_mid_resolution_still_validates`
  resolves `www.example.test.` twice through the signed fixture with a
  `Clock::Fixed`. The second resolution starts at `example.test.` from the
  cache (the first query of the second resolution goes to that zone's
  server), and the server moves the clock 3 601 s, past every cached DNSKEY
  set, while it answers. `establish_chain` then holds nothing below the
  anchor, fetches the root's DNSKEYs, finds no referral evidence for `test.`
  or `example.test.` in this resolution, and returns `Bogus(DNSSEC_BOGUS,
  "www.example.test. is signed by example.test., whose keys were never
  established")`. That is SERVFAIL for a secure answer. It fails closed, as
  the row reasoned, and it is a failure. The test is committed
  `#[ignore]`d with the reason; 151c removes the attribute.
- **The second window cannot be provoked.** `holds` and the `get` after it
  are two synchronous reads with no `await` between them. A `Clock::Fixed`
  moves only when the test moves it, and nothing a test controls runs
  between the two. It is reachable in production by two routes: the system
  clock crossing the expiry second between the reads, or a concurrent
  resolution's `insert` halving the map. Neither is deterministic, so no
  test is written for it. 151c removes the second read rather than closing
  the gap, which is the fix that needs no test to be right.

#### Agent brief — 151c

**Summary:** Validation resumes from where the resolution actually started.

**Summary:** Build two shapes of the chain walk on top of 151b and 151c, and

**Desired behavior:**

- **Baseline** is `main` from `3935df9` (151c): `establish_chain`'s loop

- **Walker** is branch `151-walker`, one commit (`a590735`) on `3935df9`:
  `dnssec_chain::ChainWalk`, which says what it needs (`ChainNeed::Keys`,

The nine rules: no anchor is Indeterminate; the walk starts at the anchor's
zone; it resumes from the deepest trusted start at or above the target;
it ignores a trusted start above the anchor; the target's own zone ends
Secure; no cut below ends Secure; a delegation verdict ends Insecure or
Bogus, or moves on with the DS set; keys the DS does not vouch for end Bogus
and are not handed back; a failed fetch is DNSKEY_MISSING; the step cap
ends Bogus. In the baseline every one of these is reachable only through
the async resolver, and 151a's case needed a fake network and a moving
clock. In the walker it is `a_walk_resumes_from_the_deepest_trusted_start`,
eleven lines.

Allocation counts are identical in `rdns/tests/allocations.rs` and
`rdnsr`'s module (12, 2, 3), but neither file counts `establish_chain`. So
this says the walker added nothing to the paths that are counted, and
nothing about what a walk costs. The walker allocates its own `KeyStore`,
which `establish_chain` extends into the caller's at `Done`. That is one
map per validation, not measured.

What it did not stall on: the trusted start's keys are copied in at
`start`, so the walker borrows nothing from the resolution and the loop
can hand `state` to `fetch_dnskeys` mutably.
