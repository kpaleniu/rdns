### 163. A TCP or DoT peer that never reads its replies holds its connection forever — **filed 2026-10-03, closed 2026-10-03**, **bug**, **ready-for-agent**

Found grilling #161. Provoked on Windows with a throwaway test against
`tcp::serve_one` at `idle_timeout` 200 ms: a client pipelining small
valid queries and reading nothing. Its sends blocked, so the server had
stopped reading; `serve_one` had not returned 10 s later, nor 10 s after
`Shutdown::begin`. Not committed.

Read, not provoked: the writer task's `write_all` has no deadline; with it
stalled the reply channel fills, handlers block in `send_framed` holding
their `in_flight` permits, and the read loop blocks in `acquire_owned`,
which races neither the idle timeout nor `stop`. Which of those holds the
task was not instrumented. `tcp::serve` holds a `Busy` per connection, so
such a peer also makes the shutdown drain wait out its budget, and it
holds a `--max-connections` slot.

DoT runs the same `serve_one`. DoH and DoQ not checked: HTTP/2 and QUIC
flow control are each their own question.

No remedy costed.

**Triaged 2026-10-03.** No write in `rdns-transport` has a deadline.
`.out-of-scope/connection-turnover-limits.md` declined a maximum
connection duration, which would have bounded this, because
`--max-connections` and the per-source limit bound what a client holds;
they still let one source keep 32 slots this way, and neither covers the
shutdown drain. Not a reopening: the remedy below is narrower.

Both halves were built in a throwaway against the probe above and
reverted:
- A deadline on the writer's `write_all` alone: still running at 10 s.
  The client keeps sending, so the read loop is not idle, and it answers
  into a channel nobody drains.
- With the read loop also leaving on `tx.closed()`, at the length read
  and at the `in_flight` wait: ended at 6.5 s against a 500 ms deadline.
  Why not sooner was not instrumented; likely the buffers filling first.
  `tcp::` tests unchanged.

That second half is a defect today on its own: after a write *error* the
read loop goes on admitting and answering queries whose replies go
nowhere.

Decided: the deadline is `read_timeout` (5 s, a constant), the leash a
message already gets once its prefix has arrived; Knot's `tcp-io-timeout`
is one value for both directions. DoH is bounded by #161's drop deadline,
read and not provoked. DoQ is #164.

#### Agent brief

**Category:** bug
**Summary:** End a TCP or DoT connection whose replies cannot be written.

**Current behavior:** A client that pipelines queries and reads nothing
stalls the writer task; `serve_one` then runs past the idle timeout and
past shutdown, holding a slot and the drain. After a write error the read
loop keeps answering into a closed channel.

**Desired behavior:**
- ~~Each `write_all` in `serve_one`'s writer task is bounded by
  `limits.read_timeout`~~ **Not the whole write (grilled, below):** each
  reply is written under a *progress* deadline of `limits.read_timeout`,
  restarted whenever any bytes go out; when nothing moves for that long
  it is counted and logged as the write error path already is, and the
  writer ends.
- One helper for that write, which #164's reply stream uses too (§7).
- The read loop ends when the writer has: `tx.closed()` beside `stop` at
  the length read, and raced against the `in_flight` permit wait.
- `TransportLimits::read_timeout`'s doc says it bounds a write too.

**Acceptance criteria:**
- [x] A test against `serve_one`: a client pipelining queries and reading
      nothing, with a short `read_timeout`; `serve_one` returns within a
      bound. Shown hanging against the current code, with the test's own
      wait bounded.
- [x] A reader taking a 64 KB reply slower than it would arrive in
      `read_timeout`, but steadily, gets all of it.
- [x] A test that a write error ends the read loop.
- [x] Workspace tests and clippy on Windows and Linux; fmt, doc and the §12
      grep clean.

**Out of scope:** DoQ (#164); a write-timeout flag.

**Grilled 2026-10-03.** A whole-write deadline cut off a slow secondary:
transfer envelopes go through the same writer (`dispatch.rs`, the
`send_framed` in the AXFR loop) at up to 64 KB, so 5 s for one was a
13 KB/s floor on every transfer. A client that reads nothing and one that
reads slowly differ in whether anything moves, which only a progress
deadline sees.

**Closed 2026-10-03**, `0d0d5f2`. As briefed. `write_progressing` in
`rdns-transport`'s root writes each reply under a deadline of
`read_timeout` restarted on every byte; `serve_one`'s read loop leaves on
`tx.closed()` at the length read and at the permit wait. `Reply::Abort` now
ends the read side as well.

Each test watched failing: the original code fails the read-nothing and
write-error tests at their bounds, a whole-write deadline fails the slow
reader, and the deadline without the `tx.closed()` arms still fails the
first two. Triage's 6.5 s was not re-measured: the read-nothing test sends
60 KB replies so the buffers fill quickly. 1438 tests on Windows, 1459 on
Linux.
