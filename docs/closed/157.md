### 157. The query and response limiters key on the peer, not the source — **filed 2026-10-02, closed 2026-10-03**, **bug**, **ready-for-agent**, before #156

Found grilling #156. `RateLimiter::buckets` and `ResponseLimiter::clients`
(`rdns/src/security.rs:116`, `:279`) are `HashMap<IpAddr, _>`: one bucket
per exact address. An IPv6 host normally holds a /64, so it can rotate
peers and be a new client to both limiters each time — the per-client limit
does not bind it. Worse, ~~read and not reproduced~~ **reproduced, below**: once `RateLimiter` holds
`max_tracked` (10 000) buckets it admits any peer it does not already track,
without a bucket (`:158`; §5's fail-open, chosen so one flood cannot deny
everyone). Peers already tracked stay limited; every new one is not — and a
/64 is an inexhaustible supply of new ones, so the host that filled the
table is then not limited at all.

`CONTEXT.md` now defines **Source** as an IPv4 address or an IPv6 /56 and
**Peer** as the exact address; `ServeContext::allow_source(peer)` reads
wrongly against that until this is fixed. BIND's response rate limiting
groups by `ipv4-prefix-length` 24 and `ipv6-prefix-length` 56 by default.

The probe that settles it: a test that sends, through
`RateLimiter::should_allow`, more than the burst from peers rotated within
one /64 — first below `max_tracked`, then past it — and asserts whether the
/64 as a whole is ever refused. (`untracked_sources` is the query logger's
counter, `logging.rs:57`, not the limiter's; the limiter has no count of
what it admitted untracked, which is a visibility gap of its own, §14.)

This row owns the source type #156 reuses. Whether query-rate limiting wants
#156's IPv4 /32 or BIND's /24 is this row's to decide, and to record. No
remedy costed.

**Triaged 2026-10-02: confirmed**, by a throwaway probe through
`should_allow` and `admit` (not committed), on Windows:

| probe | result |
|---|---|
| `RateLimiter` 10/s burst 20, one peer, 1000 queries in one second | 20 allowed |
| the same, one query each from 1000 peers in one /64 | 1000 allowed |
| table filled to 10 000, then 5000 queries from new peers in that /64 | 5000 allowed; `tracked_ips` 10 000 |
| a peer already tracked, after that | 19 of 100 allowed — still limited |
| `ResponseLimiter` 1000 B/s burst 4000, 1000-byte replies to one peer | 4 of 1000 sent in full |
| the same, to 1000 peers in one /64 | 1000 sent in full — 250× toward one network |

`RateLimiterStats` has `tracked_ips` and `total_tokens` only: nothing
counts what was admitted untracked. Two more per-peer tables have the same
shape, the logger's `queries_by_ip` and `rate_limited_ips`, which drive the
anomaly warning naming heavy hitters — so a host rotating within its /64 is
also invisible to the report meant to find it.

**A framing correction.** Triage first said the two limiters key on
different addresses. They read the same field, the query's source address;
what differs is its meaning — the sender to `RateLimiter`, where the reply
lands to `ResponseLimiter`, which for a spoofed query is the victim — and so
the grouping each can afford.

Grilled to a design (Q1-Q9). `CONTEXT.md` gains **Response target** and
says an IPv4-mapped peer is IPv4 in both terms. Decided, and rejected on the
way:
- **Two groupings.** Over the query budget a query is dropped, so a coarse
  key silences innocent neighbours: `RateLimiter` and the logger use
  **Source** (IPv4 /32, IPv6 /56). Over the response budget a reply is
  truncated or slipped and a legitimate client retries over TCP, while a
  spoofer spreading over a victim's /24 gets 256 budgets: `ResponseLimiter`
  uses **Response target** (IPv4 /24, IPv6 /56) — BIND's
  `ipv4-prefix-length` and `ipv6-prefix-length` defaults, the same split
  for the same reason. Both-Source leaves 256× toward an IPv4 /24;
  both-/24 drops queries from a shared /24.
- **Fixed constants**, not four flags; §14's rule is about rates and
  ceilings, and a grouping is a definition with its reason beside it.
- **Two newtypes**, `Source` and `ResponseTarget`, built only from a peer
  over one private masking function, so neither map can be probed by the
  other's key or by a raw `IpAddr` (§17). One parameterized type, or a
  function returning a masked `IpAddr`, lets the groupings mix again.
- **IPv4-mapped peers canonicalized first.** On a dual-stack `[::]` socket
  (Linux's default `bindv6only=0`) every IPv4 client arrives as
  `::ffff:a.b.c.d`, and `::ffff:0:0/96`'s /56 would make the whole IPv4
  internet one source.
- **Table-full policies kept**, now visible:
  `dns_rate_limiter_untracked_total` and
  `dns_response_limiter_untracked_total`. Failing `RateLimiter` closed is the
  one-flood-denies-everyone outcome its doc comment rejects; grouping is what
  makes filling the table expensive.
- **Exemption checked against the peer**: exempting a host is about that
  host, not its /56.
- The ACL's own refusal of mapped peers is **#158**.

No ADR: the constants are reversible, and their reasons go on the types.

#### Agent brief

**Category:** bug
**Summary:** Key the query limiter, the response limiter and the query
logger's per-client tables on address blocks, not exact addresses.

**Current behavior:** all four tables key on the exact peer address. An
IPv6 host rotating within its /64 is a new client every time: the query
limit never binds it, a response budget multiplies by every address
spoofed, and past `max_tracked` the query limiter admits every new peer
without a bucket and without a count.

**Desired behavior:**
- Two `rdns` newtypes, each constructible only from a peer `IpAddr`:
  **Source** — IPv4 address, IPv6 /56 — and **Response target** — IPv4
  /24, IPv6 /56. An IPv4-mapped IPv6 peer is canonicalized to IPv4 before
  either grouping — inside these types for now; #158 moves canonicalizing
  into a `Peer` type both are built from, and deletes this copy. One private
  masking function serves both; the prefix
  lengths are constants whose doc comments give the reason for each and
  cite BIND's defaults.
- `RateLimiter` keys on `Source`, `ResponseLimiter` on `ResponseTarget`,
  the logger's `queries_by_ip` and `rate_limited_ips` on `Source`; the
  anomaly warning names the block (a bare IPv4 address, or an IPv6 /56 in
  prefix notation).
- Exemption lists are still matched against the peer.
- At `max_tracked`, `RateLimiter` still admits and `ResponseLimiter` still
  truncates; each counts it, scraped as `dns_rate_limiter_untracked_total`
  and `dns_response_limiter_untracked_total`.
- #156 reuses `Source`; nothing else maps a peer to a block.

**Key interfaces:**
- `RateLimiter::should_allow` and `ResponseLimiter::admit` keep their
  signatures, taking the peer.
- `RateLimiterStats` gains the untracked count; the response limiter
  exposes its own.
- `ServeContext::allow_source` keeps its name, which now reads correctly.

**Acceptance criteria — each test shown failing against the current code
first (§1):**
- [ ] Queries from peers rotated within one IPv6 /64 are limited as one
      peer's are (20 of 1000 at 10/s burst 20 in one second, not 1000).
- [ ] Two IPv4 addresses in one /24 have separate query buckets and one
      shared response budget.
- [ ] Responses spread over one IPv6 /64, and over one IPv4 /24, are
      charged to one response target.
- [ ] A mapped peer `::ffff:192.0.2.1` and `192.0.2.1` are one source, and
      `::ffff:192.0.2.1` and `::ffff:198.51.100.1` are two.
- [ ] Past `max_tracked`, each limiter's untracked counter moves and both
      appear in the scrape.
- [ ] A rotating /64 shows up in the anomaly warning as one /56.
- [ ] `cargo test -p rdns --test allocations` counts are unchanged, or a
      count that rose has its reason beside it (§17).
- [ ] Workspace tests and clippy on Windows and Linux; fmt, doc and the §12
      grep clean.

**Out of scope:**
- Configurable prefix lengths.
- `TransferAcl`'s treatment of mapped peers (#158).
- #156's connection limit, which builds on this.

**Closed 2026-10-03**, `cccd5c0`. The design as grilled, with one interface
moved:

- **`RateLimiterStats` did not gain the untracked count.** Each limiter's
  `judge` returns the verdict and whether the table had room, and
  `ServeContext` — the one caller in either daemon — counts the second into
  the two scrape counters. A count in the limiter as well would be a second
  copy of one event. `should_allow` and `admit` keep their signatures as
  wrappers.
- The logger's maps were renamed `queries_by_source` and
  `rate_limited_sources`, since a counter's name is a claim about what it
  counts (§14); one `rdnsr` test read the old name.

Two `security` tests had encoded the per-address keying and were changed:
one put a noisy and a quiet client in one /24, the other filled the table
from one /24. The four acceptance tests failed against the old limiters with
the triage probe's numbers (1000 for 20, 1000 for 4); with the mask made an
identity they fail again, and so does the logger's /56 test. All 51 counts in
`rdns/tests/allocations.rs` are unchanged. 1405 tests on Windows, 1426 on
Linux.
