### 161. A DoH connection is never closed for being idle — **filed 2026-10-03, closed 2026-10-03**, **bug**, **ready-for-agent**

Found closing #155, whose row said all four stream listeners close a
connection idle for 10 s. Three do: `tcp::serve_one` times its length read
(TCP and DoT) and `quic::server_config` sets `max_idle_timeout`. DoH hands
the TLS stream to hyper, and `https::serve` reads `limits` only for
`max_connections`: neither builder is given a timer, and hyper's HTTP/2
server has no idle close at all (its `keep_alive_*` are pings).

Provoked on Windows with a throwaway test against `https::serve` at
`idle_timeout` 200 ms: a TLS connection sending nothing, and one sending
only the HTTP/2 preface, were both still open after 3 s. Not committed.

So an idle DoH connection holds one of `--max-connections` slots until the
client closes it, and a peer that opens 128 and sends nothing holds the DoH
listener full indefinitely — which #155 makes visible and not bounded.
`--connection-idle-timeout`'s help says it does not apply to DoH.

No remedy costed. What "idle" means here is the open question: no bytes in
either direction, or no request in flight, since an HTTP/2 connection can be
silent while a recursion behind one of its streams is still running.

What the others do, read from source, none provoked:

| | setting, default | shared with TCP | clock resets on | in flight holds it | close |
|---|---|---|---|---|---|
| BIND | `tcp-idle-timeout`, 30 s | yes | a completed request | no | abrupt |
| Unbound | `tcp-idle-timeout`, 30 s | yes | any read or write | no | abrupt |
| Knot Resolver | `tcp_in_idle`, 10 s | yes | a query or a reply | yes | TLS close |
| dnsdist | `idleTimeout`, 30 s | no | any bytes | yes | stops reading |
| CoreDNS (Go) | `IdleTimeout`, 10 s | yes | a stream opening | yes | GOAWAY |

Grilled to a design. Decided, and rejected on the way:
- **Idle is no new request started**, whatever is in flight: what
  `tcp::serve_one` already means. Rejected: no bytes either way (a client's
  PINGs would hold the slot), and no request in flight (a second meaning
  of one flag on one transport).
- **Closed gracefully**: GOAWAY, or the HTTP/1 exchange finished, so an
  in-flight answer is delivered.
- **Dropped one more idle timeout after that** if it has not closed: a
  peer that stops reading stalls HTTP/2 flow control, and one sending
  HTTP/1 headers a byte at a time never finishes a request; unbounded,
  either holds the slot this row is about. Rejected: waiting without a
  limit, and a separate fixed deadline.
- **`--connection-idle-timeout`, same default.** Four of the five share one
  setting with TCP.
- **One timer in `https::serve`** for both protocols, not hyper's HTTP/1
  `header_read_timeout`, whose clock starts after a response — the other
  meaning, on one protocol.

#### Agent brief

**Category:** bug
**Summary:** Close a DoH connection on which no request has started for
`--connection-idle-timeout`.

**Current behavior:** After the handshake, a DoH connection is held until
the client closes it, so idle clients can hold every `--max-connections`
slot.

**Desired behavior:**
- Per connection, a deadline of `idle_timeout`, restarted whenever a
  request reaches the service. In flight does not stop the clock.
- On expiry, `graceful_shutdown` on the hyper connection, HTTP/1 or
  HTTP/2. If the connection has not finished one `idle_timeout` later, it
  is dropped.
- `--connection-idle-timeout`'s help in both daemons and
  `docs/CLI_USAGE.md` say it applies to DoH: closed gracefully, dropped
  one timeout later.

**Acceptance criteria:**
- [ ] HTTP/2: a connection that sends the preface and SETTINGS and no
      request reaches EOF within a bound, and with one slot the next
      client is answered.
- [ ] HTTP/1.1: a keep-alive connection, after one answered request,
      reaches EOF within a bound.
- [ ] ~~A request whose handler takes twice `idle_timeout` is still
      answered.~~ **Wrong, by the design two bullets up:** the drop comes
      one timeout after the graceful close, which is itself one timeout
      after the request, so twice is the boundary and a race. Tested at
      half again.
- [ ] A connection sending a partial HTTP/1.1 header and nothing more is
      dropped by about twice `idle_timeout`.
- [ ] Each shown failing against the current code, with the test's own
      waits bounded.
- [ ] Workspace tests and clippy on Windows and Linux; fmt, doc and the §12
      grep clean.

**Out of scope:** the stream listeners' reply writer (#163); a
DoH-specific flag.
