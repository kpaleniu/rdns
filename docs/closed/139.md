### 139. TSIG reads a key name off the wire as lossy, unescaped text — **filed and closed 2026-09-28**, **bug**

Found by the idiom review of 2026-09-28. `read_name_at` and `read_name`
(`rdns-tsig/src/tsig.rs:1050`, `:1082`) build the owner and algorithm names
with `String::from_utf8_lossy` per label and `join(".")`, with no RFC 1035
§5.1 escaping. The key name then goes to the keyring by that text and into
the digest by `name_wire(&key_name)` (`:499`), which parses it as
presentation.

Provoked with `sign_request` then `check_request`, one key, one keyring:

| key name | our own request |
|---|---|
| `plain.key.` | verified |
| `a\.b.` | rejected, key read as `a.b.` |
| `k\200ey.` | rejected, key read as `k\u{FFFD}ey.` |

Not a bypass: the MAC is still checked, and a mis-read name matches nothing
or fails verification. It is a second name parser beside `rdns_core::Name`,
which `rdns-tsig` already depends on (§7), and it disagrees with ours.
`skip_name` and `skip_record` beside them are allocation-free on purpose
(`:930`), and they stay.

> *This was generated by AI during triage.*

**Agent brief.** Read both names with `rdns_core::Name`'s wire parser and
carry the key name in presentation form from `to_presentation()`, so that
escapes survive into `canonical_key_name` and `name_wire`. The three rows
above are the test. Check `allocations.rs` for a count on the TSIG path
before and after.

**Closed 2026-09-28**, `248bdc0`. `Name::from_wire_in` / `from_wire` and
`to_presentation`. A signed request now allocates the name and its text, not
one `String` per label and a join; the unsigned paths `allocations.rs` holds
at 0 do not reach it. The test covers `\.`, `\200` and `\032`, and failed at
`a\.b.` against the old reader.
