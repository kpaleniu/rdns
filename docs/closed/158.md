### 158. On a dual-stack socket, IPv4 rules do not match IPv4 clients — **filed 2026-10-02, closed 2026-10-03**, **bug**, **ready-for-agent**, after #157

Found grilling #157. Nothing in the tree canonicalizes an IPv4-mapped IPv6
peer (no `to_canonical` or `to_ipv4_mapped`), and `TransferAcl` refuses on
purpose to match an IPv4 rule against one — `test_families_do_not_mix`,
the rule `CLAUDE.md` §7 cites: "a v4 prefix never matches a v4-mapped v6
peer". Both daemons default to an IPv4 listen address, but an operator
binding `[::]` on Linux gets a dual-stack socket (`bindv6only=0` by
default), where every IPv4 client arrives as `::ffff:a.b.c.d`. ~~Read, not
provoked~~ **confirmed link by link, below**: `--allow-transfer
192.0.2.0/24` would then refuse the secondary
at `192.0.2.5`, and `--query-rate-exempt` and the NOTIFY sender lists would
not match their IPv4 hosts. It fails closed, unlike #157.

The probe: bind `rdnsd` to `[::]` on Linux, transfer from an IPv4 secondary
an IPv4 rule allows, and read the verdict. Whether the fix is canonicalizing
in `TransferAcl`, in the accept path, or a refusal to start on a dual-stack
socket with IPv4 rules is open — the family rule is deliberate, so its
reason has to be answered first (§19). No remedy costed.

Nothing sets `V6ONLY`. On Windows it defaults to on, so there `--host ::`
is IPv6-only and this cannot happen — the same configuration differs by
platform, which is **#159**.

**A fourth comparison** the row missed, outside `TransferAcl`: `rdnsd`
matches a NOTIFY's sender to its masters by exact `IpAddr` equality
(`replication.rs:147`), so an IPv4 master's NOTIFY matches nothing on a
dual-stack socket and the zone waits for its refresh timer.

**The family rule's reason, answered (§19).** "Which would be a way around
the list" (`security.rs:545`) holds for half the traffic. Linux drops
incoming TCPv6 with an IPv4-mapped source, and a TCP peer completed a
handshake anyway, so a mapped stream peer is the IPv4 host it names. The
drop was later weakened to TCP and DCCP only, so a UDPv6 datagram claiming
`::ffff:a.b.c.d` is delivered. What each check grants:

| check | transport | grants |
|---|---|---|
| `--allow-transfer` | stream only | the zone; the handshake proves the address |
| master NOTIFY (`rdnsd`) | mostly UDP | an SOA query to the real master — nothing |
| `--rpz-notify-from` (`rdnsr`) | mostly UDP | a feed refresh — nothing |
| `--query-rate-exempt` | UDP and stream | exemption from the query limit |

Grilled to a design (Q1-Q6). Decided, and rejected on the way:
- **Canonicalize every peer once, at the receive boundary** (§2). The one
  grant this opens to spoofed UDP is query-limit exemption for an exempt
  IPv4 host claimed from an IPv6 network; the reply goes to the real IPv4
  host and `ResponseLimiter` still bounds it — "the control that actually
  stops amplification" — and plain IPv4 spoofing gives the same grant where
  BCP 38 is not applied. Rejected: `IPV6_V6ONLY` everywhere, which keeps the
  rule as written but takes IPv4 off every `--host ::` on Linux and needs a
  multi-address `--host` to undo; canonicalizing per check, which is four
  checks under two policies with the transport threaded into each; refusing
  to start, which rejects a configuration this makes work.
- **A `Peer` newtype whose only constructor canonicalizes**, taken by every
  check (§17); `canonical(ip)` at each arrival point is the call-site fix
  §17 measured recurring. `CONTEXT.md`'s **Peer** now says canonical, and
  **Source** and **Response target** are blocks *of a peer*.
- **#157 first**: it is confirmed and fails open; this one fails closed.
  #157's types canonicalize themselves until this lands and removes that.
- **Proved on both platforms**: the test builds its own dual-stack listener
  with `IPV6_V6ONLY` 0, so it does not depend on an OS default (§1).
- `CLAUDE.md` §7 and `TransferAcl`'s doc comment describe today's code, so
  they are corrected with the fix, not now.

No ADR: the reason goes on `Peer` and in §7.

#### Agent brief

**Category:** bug
**Summary:** Every peer address is canonical from the moment it is read, so
an IPv4 client on a dual-stack socket matches IPv4 rules.

**Current behavior:** on a dual-stack `[::]` listener an IPv4 client's
address is `::ffff:a.b.c.d`, and four checks miss it: `TransferAcl` for
`--allow-transfer` and `--query-rate-exempt` and `--rpz-notify-from`
(families never match, on purpose), and `rdnsd`'s NOTIFY master match
(exact equality).

**Desired behavior:**
- A `Peer` type in `rdns` holding an address whose only constructor maps an
  IPv4-mapped IPv6 address to its IPv4 address. Its doc comment gives the
  reason, including the TCP/UDP asymmetry and the one UDP grant it opens.
- Each daemon's UDP receive loop and each stream arrival point (TCP/DoT
  accept, DoH, DoQ) builds a `Peer` from the socket's address before
  anything else sees it.
- Every check takes a `Peer`: `TransferAcl::allows`, the NOTIFY master
  match, the rate and response limiters, and #157's `Source` and
  `ResponseTarget` — whose own canonicalization is deleted.
- Logs, the query logger and dnstap record the canonical address; the
  commit names that as a visible change for dual-stack deployments.

**Key interfaces:**
- `Peer`: constructible from an `IpAddr` or a `SocketAddr`; converts back
  to `IpAddr` for display and for replies.
- `TransferAcl::allows(Peer)`; the family rule now means "after
  canonicalizing".

**Acceptance criteria — each test shown failing against the current code
first (§1):**
- [ ] A test builds a dual-stack listener (`IPV6_V6ONLY` 0 via `socket2`),
      serves an AXFR on it with `--allow-transfer 127.0.0.1`, connects from
      `127.0.0.1`, and gets the zone. It runs on Windows and Linux.
- [ ] A NOTIFY from an IPv4 master over a dual-stack socket is accepted.
- [ ] `Peer` unit tests: `::ffff:192.0.2.1` is `192.0.2.1`; `::1` and
      `2001:db8::1` are unchanged; `::192.0.2.1` (the deprecated
      IPv4-compatible form) is unchanged.
- [ ] A raw `IpAddr` reaches no check — the checks' signatures take `Peer`.
- [ ] `CLAUDE.md` §7's "a v4 prefix never matches a v4-mapped v6 peer" is
      struck through with the corrected rule and a pointer here (§11), and
      `TransferAcl`'s doc comment gives the new reason.
- [ ] Workspace tests and clippy on Windows and Linux; fmt, doc and the §12
      grep clean.

**Out of scope:**
- Making `--host ::` mean the same on both platforms (#159).
- `--dns64-exclude`, which matches answer data, not peers.

**Closed 2026-10-03**, `edfd99a`. The design as grilled, with two
corrections to the brief:

- **Five checks, not four.** `PolicyZones::before_query` matched RPZ
  client-IP triggers against the raw peer, and
  `a_v4_client_rule_does_not_match_a_mapped_v6_client` asserted it, citing
  `TransferAcl`'s rule. It takes a `Peer` now and the test is reversed.
- **`Peer` does not convert back "for replies".** A dual-stack socket
  reports an IPv4 client as `::ffff:a.b.c.d` and a reply has to go there, so
  both UDP loops keep the address the socket reported for `send_to` and build
  the canonical one for everything else. The NOTIFY test is what shows the
  reply arrives.

Each arrival point canonicalizes the `SocketAddr` once
(`rdns::peer::canonical`), which is what puts the IPv4 form in logs, the
query logger and dnstap; every check takes `Peer`, whose only constructor
canonicalizes, so a call site that skipped the first step still checks the
right address. The two dual-stack tests set `IPV6_V6ONLY` 0 through
`socket2` (a dev-dependency of `rdnsd`, already in the lock) and failed on
Windows against `4335734`. Allocation counts unchanged. 1408 tests on
Windows, 1429 on Linux.
