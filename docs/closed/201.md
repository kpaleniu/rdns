### 201. No release pipeline: nothing is built from a tag — **filed 2026-10-10**, **enhancement**, **triaged 2026-10-10**, **closed 2026-10-10**

`git tag | wc -l` is 0 and `.github/workflows/` holds only `ci.yml`, which
runs on pushes to `main`/`master` and on pull requests; a tag push matches
neither. Every crate is `0.1.0` (`Cargo.toml:21`). The version a binary
reports comes from `git describe` (`rdns-core/build.rs`), and CI's `image`
job already derives it from `github.ref_name` on a tag. #194 (Windows
installer) is blocked on a release artifact.

Wanted: a workflow triggered by pushing a tag, plus `workflow_dispatch` for a
re-run against an existing tag. Never on a branch push: Actions minutes are
billed per run.

For triage:

- Which binaries (`rdnsd`, `rdnsr`, `rdnsc`, `rdnsctl`) on which targets.
  CI tests Linux and Windows only.
- Where the container image goes: a registry, or a release asset.
- Whether a tag must equal the workspace `version`, and what fails if not.
- Checksums or signatures on the assets.
- Whether the release runs the `ci.yml` jobs first or trusts the commit's
  earlier run.

## Triage decisions (2026-10-10)

- Targets: `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, the two CI
  tests. Others get their own item.
- One archive per target: `rdnsd`, `rdnsr`, `rdnsc`, `rdnsctl`, `LICENSE`;
  `.tar.gz` on Linux, `.zip` on Windows.
- Tag `vX.Y.Z` must equal the workspace `version`, or the run fails.
- Releasable means `ci.yml` succeeded on the tagged commit. It runs per push
  on the head, with `cancel-in-progress`, so a batched push's intermediate
  commits have no run and cannot be released.
- `SHA256SUMS` only. Build-provenance attestations need Enterprise Cloud on a
  private repository.
- Draft release; the owner publishes. Notes are `git log --oneline` since the
  previous tag (all history for the first), edited before publishing.
- Image to `ghcr.io/<owner>/rdns:X.Y.Z` on the tag push (private package);
  `:latest` is moved by a second workflow on `release: published`, re-tagging
  the pushed image without a rebuild.

## Brief

> *This was generated by AI during triage.*

**Category:** enhancement
**Summary:** Build a draft GitHub release and a versioned container image
from a pushed version tag.

**Current behavior:** no tags, no release workflow. `ci.yml` runs on branch
pushes and pull requests only; its `image` job already derives the version
stamp from `github.ref_name` on a tag.

**Desired behavior:**
- A workflow triggered by pushing a tag matching `v*`, and by
  `workflow_dispatch` with a tag input to re-run an existing tag. Never by a
  branch push.
- It fails, before building, if the tag is not `v` + the workspace
  `version`, or if no successful `ci.yml` run exists for the tagged commit.
- It builds release binaries for the two targets, archives them as decided
  above, writes `SHA256SUMS` over the archives, and creates or updates a
  draft release with those assets and the `git log` notes.
- It builds the image with `RDNS_GIT_DESCRIBE` set to the tag and pushes
  `ghcr.io/<owner>/rdns:X.Y.Z`; `<owner>` from `github.repository_owner`,
  lowercased.
- A second workflow on `release: published` adds `:latest` to that image's
  manifest without rebuilding.
- Each binary's `--version` names the tag.

**Acceptance criteria:**
- [x] The workflows parse (`actionlint` clean, or the reason it cannot run).
- [x] The version and CI-success checks are a script runnable locally, and
      shown failing for a mismatched tag and for a commit with no green run.
- [x] A dispatch re-run of an existing tag replaces the draft's assets rather
      than duplicating them.
- [x] Nothing is pushed or tagged by the agent. The first end-to-end run is
      the owner's tag push; the brief is done when the workflows are
      committed and the local checks pass.

**Out of scope:** other targets; signing; publishing crates; a changelog
file; the Windows installer (#194).
