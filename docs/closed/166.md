### 166. A DoQ stream answered slower than the idle timeout is lost when the client is silent — **filed 2026-10-03, closed 2026-10-04**, **not a defect**

Found closing #164. `quic::server_config` hands `--connection-idle-timeout`
to quinn as `max_idle_timeout`, and RFC 9000 §10.1 restarts that timer on a
packet received, or on the first ack-eliciting packet sent after one. A
client that sends its query and then nothing — no PINGs — gives the server
nothing to restart it with while the handler works, so a reply that takes
longer than the idle timeout is never sent: the connection times out under
it.

Provoked on Windows, throwaway and reverted: idle timeout 300 ms, a handler
pausing 450 ms, a quinn client with default transport settings. The stream
read `ConnectionLost(TimedOut)`, against `9fa0fa5`'s code and against the
code before it, so #164 neither caused nor fixed it. With the client sending
PINGs the same stream is answered
(`a_stream_in_flight_at_the_idle_timeout_is_answered`).

~~TCP and DoH have no such timer, so a slow answer there is bounded by the
handler alone: this is DoQ's only.~~ **Half wrong** (grilling, 2026-10-04): TCP
is bounded by the handler alone, but DoH is not — `https.rs`'s `until_idle`
drops a connection one `idle_timeout` after its graceful close, answer in
flight or not, as `quic.rs`'s own drain does. At the default 10 s it needs a
handler slower than ten seconds; how long `rdnsr`'s slowest resolution can take was
not checked. **Checked closing it**: four silent nameservers take 10 s, and
a resolution can run to 157.5 s — #168. No remedy costed.

**Closed 2026-10-04**, `284ff25`: not a defect. RFC 9250 gives the watch to
the client. §4.4: "Clients SHOULD monitor the idle time incurred on their
connection to the server, defined by the time spent since the last packet from
the server has been received." §5.5.2: "Clients that want to maintain long
duration DoQ connections SHOULD use the idle timeout mechanisms defined in
Section 10.1 of [RFC9000]." The RFC says nothing of server PINGs. The idle
timeout in use is the minimum of both ends' (§4.4), so the silent client times
the connection out on its own side as well.

No other DoQ server sends keep-alive PINGs, by a grep for
`keepalive|KeepAlive|ping|ack_eliciting` rather than a read of every path:

- dnsproxy `f2a42ab`, `proxy/serverquic.go`: `MaxIdleTimeout` 30 s, fixed; no
  `KeepAlivePeriod`.
- CoreDNS `92129ac`, `core/dnsserver/server_quic.go`: `MaxIdleTimeout` from
  the server's `IdleTimeout`, 10 s by default; no `KeepAlivePeriod`.
- Knot `7d3a429`, `src/libknot/quic/quic.c`: `max_idle_timeout` from
  `quic-idle-close`, 4 s by default; no ping.
- Unbound `eafb027`, `services/listen_dnsport.c`: `max_idle_timeout` from
  `tcp-idle-timeout`, 30 s by default; no ping.
- dnsdist `afd6e83`, `doh3.cc`: `idleTimeout`, 5 s by default; no ping.
- NSD has no DoQ; none was found in BIND.

Whether quiche or ngtcp2 send a PING of their own while a stream is open was
not read.

`a_silent_client_loses_a_stream_slower_than_the_idle_timeout` pins the
behaviour, so a server keep-alive has to be added on purpose. The real cost
this found is a resolution with no deadline, on every transport: #168.
