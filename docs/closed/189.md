### 189. `rdnsr` cannot ask its upstreams for NSID — **filed 2026-10-06, closed 2026-10-07**, **enhancement**

Found triaging #179, which is the other direction: answering NSID. RFC 5001
§2.1 makes the two independent: "if the resolver side of the recursive name
server wishes to receive identifying information, it is free to add NSID
requests in its own queries, but that is a separate matter."

What it would buy: when an anycast authority or forwarder hands back a bad
answer — a stale zone, a broken signature — the log would name the instance,
not only the shared address. Today `rdnsr` sees the address alone.

Peers, checked in their reference documentation on 2026-10-06:

- BIND `request-nsid`, default `no`: "an empty EDNS(0) NSID (Name Server
  Identifier) option is sent with all queries to authoritative name servers
  during iterative resolution. If the authoritative server returns an NSID
  option in its response, then its contents are logged in the `nsid`
  category at level `info`."
- Unbound: `nsid:` answers only; no outbound option in `unbound.conf(5)`.
- PowerDNS Recursor: `server-id` answers only; no outbound option in its
  settings table.
- Knot Resolver: not checked.

Searched: `build_query` (`rdns/src/resolver.rs`) sends an OPT with payload
size and DO, and no options. No remedy filed beyond what BIND does; whether
the identifier goes to the log, to dnstap, or both is triage's call.

**Triaged 2026-10-07: enhancement, ready-for-agent.**

**Category:** enhancement
**Summary:** `--request-nsid` makes `rdnsr` ask every upstream for NSID and
log which instance answered, at INFO only when that changes.

**Current behavior:** `build_query` sends an OPT with payload size and DO and
no options. An upstream reply's NSID, if any, is never read. `rdnsr` has no
dnstap (#191), so nothing else records which instance of an anycast server
answered.

**Desired behavior:**

- `--request-nsid`, `request-nsid` in `[resolver]`, off by default (BIND's
  `request-nsid` default `no`).
- When on, every upstream query — to authorities and to forwarders — carries
  an empty NSID option (RFC 5001 §2.1: "The resolver MUST NOT include any
  NSID payload data in the query message").
- A reply's NSID is rendered as text when it is printable ASCII, else as hex:
  §2.3 makes it opaque bytes, and a log line must not carry raw control
  characters.
- Logging: DEBUG for every reply carrying NSID; INFO when the NSID seen from
  a server address differs from the last one seen from it — the anycast node
  behind the address changed, which is the signal. The last-seen table is
  bounded like the RTT store (§5). A reply that fails validation or is
  otherwise rejected logs its server's NSID at that failure's own level.
- Never transitive: an upstream's NSID never reaches a client's reply
  (§2.1–2.2); #179 answers clients with `rdnsr`'s own.
- No counter: identifiers are an unbounded label set (§5).

**Acceptance criteria:**

- [ ] Off: upstream queries carry no NSID option (assert at a mock).
- [ ] On: every upstream query carries an empty NSID option.
- [ ] A mock answering NSID `node-a`: one INFO line naming the server, the
      question and `node-a`; the second identical reply logs at DEBUG only.
- [ ] The mock switches to `node-b`: one INFO line.
- [ ] A non-ASCII NSID is logged as hex.
- [ ] A bogus reply from a mock logs its NSID with the failure.
- [ ] The client's reply never carries the upstream's NSID.
- [ ] More distinct server addresses than the bound: the table stays at its
      bound.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit.

**Out of scope:**

- dnstap for `rdnsr` (#191).
- Per-identifier metrics.

**Closed 2026-10-07**, `262fe23`. As briefed, with the INFO/DEBUG decision returned by `NsidStore::observe` so it is tested without a log subscriber in `rdns`. The bogus case names the NSID in `Bogus::why`, which is what `rdnsr`'s existing WARN prints, rather than a second line. 1500 tests on Windows, 1521 on Linux.
