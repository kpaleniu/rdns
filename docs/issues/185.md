### 185. The UDP path: what the throughput figures measured, and where the remaining cost is — **filed 2026-10-05**, **triaged 2026-10-05**

Filed after a comparison against Knot, NSD and BIND took #28d's ~170k q/s as
`rdnsd`'s ceiling. It is not. Measured 2026-10-05 on Linux in a virtual
machine: server pinned to 8 vCPUs (4 cores, SMT), `dnsperf -c 16 -T 8 -q 1000`
pinned to the other 8, loopback, `www.example.com A` against a four-record
zone, `--query-rate 0 --response-rate 0`, 10 s runs, three of each.

| server | q/s at saturation | CPU µs/query |
|---|---|---|
| `rdnsd`, default workers (8) | 934k-962k | 8.0-8.3 |
| bare tokio responder, same shape (8 tasks, one socket, canned reply) | 958k-1.01M | 7.1-7.5 |
| bare tokio, 8 `SO_REUSEPORT` sockets | 821k-977k | 6.7-7.4 |
| bare std blocking, 8 `SO_REUSEPORT` sockets | 746k-847k | 6.2-6.5 |

~~`rdnsd` is within 5-10% of a responder that does no DNS at all.~~
**Within noise of it, not 5-10% below:** the same unchanged bare binary ran
958k-1.01M in this session and 818-877k in a later one, and throughput drifts
10-25% from one server start to the next on this VM. The table compares one
start per row, which is how 185b's 745k came about. Compare variants by
alternating runs within one session. `perf record`
at saturation: kernel 78.7% (of which 26% is spinning on the *client's*
socket wake-up lock inside the server's `sendto` — loopback delivers inline),
`rdns*` 10.6%, tokio 4.6%, allocator 0.3%, user-space locks about 1.6%. The
allocation work (`rdns/tests/allocations.rs`) has left nothing measurable in
the allocator; what is left is one `recvfrom` and one `sendto` per answer.

Caveats: a VM inflates wake-ups and spinlocks; loopback charges each side for
the other's receive; `perf stat` with tracepoints costs about 25% of
throughput, so CPU figures from those runs are high by that much. Peers'
published figures (Knot's 400G page: Knot 30M, NSD 15M, BIND 3.3M on 128
cores with a NIC and an XDP generator) are not comparable to these and are
quoted only for the order of magnitude.

#### 185a. #28d's figure measured the client — **closed 2026-10-07**

`rdns/examples/udp_flood.rs:85-93` keeps one query in flight per thread
(`send_to`, then a blocking `recv_from`) and re-parses the target string on
every send (`:86`). At 16 threads 165k/s is a ~97 µs round trip (Little's
law): latency through the VM, not a ceiling. #28d said the plateau was the
client; the number was quoted as a throughput anyway. Either make the
generator open-loop with a window, or name it a latency probe and point at
dnsperf. Correct `docs/closed/028.md` in place (#184).

**Closed 2026-10-07**, `6ab483a`: named a latency probe that prints the round
trip its rate implies, pointed at dnsperf, target parsed once. `028.md` was
corrected under #184.

#### 185b. Below saturation, more workers double the CPU per query — **needs-info**

At a fixed 20k q/s, per answer:

| config | CPU µs/q | futex | ctx-sw | `recvfrom` EAGAIN |
|---|---|---|---|---|
| `--udp-workers 1` | 35.6 | 0 | 0.15 | 0.20 |
| `--udp-workers 2` | 78.0 | 1.36 | 1.13 | 0.46 |
| `--udp-workers 8` | 72.6 | 1.24 | 0.87 | 1.59 |
| `--udp-workers 16` | 80.8 | 1.49 | 1.00 | 3.74 |
| workers 8, `TOKIO_WORKER_THREADS=1` | 36.2 | 0 | 0.13 | 0.87 |
| bare tokio, one shared socket, 8 tasks | 71.7 | 1.44 | 1.05 | 2.17 |
| bare tokio, 8 `SO_REUSEPORT` sockets | 48.5 | 0.53 | 0.49 | 0.81 |

Two effects, separable in the table:

- **The multi-thread runtime wakes a parked thread per datagram.** The step
  from 36 to 72-80 µs comes at two workers and goes away with one runtime
  thread; the bare responder shows the same. A single task on the 8-thread
  runtime saturates at 30-35k q/s against 69k on one runtime thread and
  100k+ for a blocking loop.
- **Thundering herd on the shared socket.** tokio's `ScheduledIo::wake`
  wakes every task waiting on READABLE; one wins and the rest get EAGAIN.
  EAGAIN per answer tracks worker count; each costs about 4 µs.

Both vanish at saturation (futex 0.03/q, EAGAIN 0.002/q), so this is CPU
spent at ordinary load, not lost throughput. ~~Also on the path, per
iteration: a `select!` on `Stop::wait()` (`rdnsd/src/main.rs:1164`), which
builds a watch receiver and registers on a `Notify` each time; in the bare
responder adding it cost 958k → 745k q/s.~~ **Variance, not cost** — see the
second triage note.

**Triaged 2026-10-05, needs-info.** The 958k → 745k figure contradicts
`rdnsd`, which has that `select!` and ran at 934k-962k; one of the two runs
is not measuring what it says. Re-measure before acting. If it is real, one
`stop.wait()` future pinned outside the loop is the fix. The wake-up cost is
CPU at ordinary load, not throughput: about 0.7 of a core at 20k q/s. Per-
worker `SO_REUSEPORT` sockets cut it 72 → 49 µs/q in the bare responder, at
the price of a Unix-only bind path; whether Windows and macOS balance across
such sockets is unchecked.

**Re-measured 2026-10-05: the `select!` half is withdrawn.** Four shapes in
the bare responder, three alternated runs each, dnsperf `-c 256`:

| per iteration | q/s, median [range] | CPU µs/q (user) |
|---|---|---|
| no `select!` | 1014k [1009-1019] | 5.53 (0.51) |
| `Notify::notified()` per recv (the 745k variant) | 1011k [1009-1022] | 5.69 (0.64) |
| `watch` receiver per recv, as `Stop::wait` | 999k [989-1012] | 5.74 (0.68) |
| one stop future, pinned outside the loop | 1018k [1010-1034] | 5.60 (0.60) |

About 0.1-0.2 µs/q of user CPU and no measurable throughput. The 745k
variant was the second row's code; rebuilt unchanged and alternated with
the plain loop it read 908k, 860k, 842k against 818k, 851k, 849k. It was one
start of each, a sample of the drift noted above.

What is left is the wake-up cost, still **needs-info**: the `SO_REUSEPORT`
figure came from single runs, and a repeat at 20k q/s read 66 → 57 µs/q
rather than 72 → 49. It needs alternated repeats before it is acted on.

#### 185c. One syscall per datagram — **wontfix**

Every configuration is exactly one `recvfrom` and one `sendto` per answer;
`recvmmsg`/`sendmmsg` are never called (counted with `perf stat` on the
syscall tracepoints). That kernel round trip is about 78% of server CPU at
saturation and the only remaining lever on it. Knot and NSD batch with
`recvmmsg`/`sendmmsg` on per-thread `SO_REUSEPORT` sockets; BIND 9.20 uses
libuv's `UV_UDP_RECVMMSG`. Not measured here: no batching variant was built.

**Triaged 2026-10-05, needs-info: prototype in the bare responder first.**
Batching does not mean working around tokio: `UdpSocket::try_io`/`async_io`
run a caller's syscall under tokio's readiness. The receive half costs no
package and no `unsafe`: `quinn-udp` 0.5.15 is already in the lock through
`quinn`, and its `recv` is `recvmmsg` in batches of 32 on Linux with a
one-datagram fallback elsewhere. Its batched send is GSO, one destination
per call, so it cannot send replies to many clients; `sendmmsg` would be
`libc` directly, the first `unsafe` outside tests, Linux-only. The ripple is
in `rdnsd`, not tokio: `Wire::Datagram` sends inline (`dispatch.rs:134`), so
a batch needs a collecting sink and a reply buffer per slot, which is #39b's
declined shape C. Batching only helps a backed-up socket; below saturation
`recvmmsg` returns one. It saves syscall entry, not per-packet stack work or
the loopback wake-up, so the gain is unknown.

Decision rule: receive-only, then receive plus send, each in the bare
responder on the same harness. Under ~15% for both is wontfix with the
figure. If receive alone carries it, take that half only.

io_uring was considered and is not the next step: it removes the readiness
loop and the per-call syscalls but not the per-packet kernel cost, needs its
own runtime beside tokio and kernel-owned buffers, and is commonly blocked by
container seccomp profiles. If batching does not move the number, io_uring
will not move it much either.

**Prototyped 2026-10-05: wontfix on this evidence.** Bare tokio responder, 8
tasks, one shared socket, three alternated runs each; receive batching is
`quinn-udp`'s `recv` under `async_io`, send batching `libc::sendmmsg`:

| | `-c 16` q/s | `-c 256` q/s | `-c 256` CPU µs/q |
|---|---|---|---|
| no batching | 833k | 1014k | 5.53 |
| receive batching | 1057k (+27%) | 1041k (+3%) | 5.63 |
| receive + send batching | 1005k (+21%) | 1036k (+2%) | 5.60 |

- At `-c 256` syscalls fall from 2.0 to about 0.4 per answer (5.7 datagrams
  per `recvmmsg`) and CPU per query does not move: syscall entry is not the
  cost, per-packet stack work is.
- The `-c 16` gain is on the shape where loopback's inline delivery into the
  client's socket contends most; not profiled. Resolver traffic arrives from
  many source sockets, which is the `-c 256` shape.
- Send batching adds nothing over receive batching.
- Below saturation batches average about one datagram (`-Q 20000`).
- On 8 `SO_REUSEPORT` sockets: +2% at `-c 256`, +8-20% at `-c 16` with
  ranges overlapping the baseline.

Passes the 15% bar on one client shape and fails on the other, and the one it
passes is the shape the test setup distorts most.

**Reopen if** a measurement on a real NIC, client and server on separate
hosts, shows receive batching at +15% or more with many client sockets. A NIC
takes the client's receive out of the server's `sendto`, which makes syscall
entry a larger share of what is left; this setup cannot show that. If
reopened, take receive batching only: no `unsafe`, no Linux-only send path,
and `Wire` keeps sending inline.

#### 185d. Shared state per query — **wontfix**

Six global locks per query (rate limiter, `QueryLogger`, response limiter,
the zone map's `tokio::sync::RwLock` release, `ScheduledIo`'s waiter list,
a `Notify` shard) and about twenty shared atomic writes, eight of them
adjacent unpadded metrics counters (`rdns/src/metrics.rs:215-378`). Measured
at about 1.6% of CPU at 1M q/s; contention at the cache-line level was not
measured (no `perf c2c` on the machine). Recorded so the next step past
185c knows what it meets, not as work in its own right.

**Triaged 2026-10-05, wontfix** at 1.6% of CPU. Reopen under a new letter if
185c is reopened and moves the ceiling far enough that this becomes the wall.
