### 190. Neither daemon can run as a Windows service — **filed 2026-10-07**, **enhancement**, **ready-for-agent**

Split from #188, which gives Windows a control channel; starting and stopping
under the Service Control Manager is a separate question.

What exists: `rdns::shutdown` stops cleanly on the console events —
`ctrl_c`, `ctrl_break`, `ctrl_close`, `ctrl_shutdown` (the Windows half of
`rdns/src/shutdown.rs`,
`CLAUDE.md` §4's account of why all four are needed). Searched: no service
dispatcher, no `SERVICE_` handling, no `windows-service` crate in the tree.

Not checked, and each needs checking before a remedy is named (§18, §19):
whether `sc.exe create` on either binary starts at all without a dispatcher;
what a service wrapper (NSSM, WinSW) sends on stop and whether the handlers
above catch it; whether `windows-service` or `windows-sys` is the cheaper
route, given that `windows-sys` is already in `Cargo.lock` and the tree has no
`unsafe` outside test allocators.

## Agent brief

> *This was generated by AI during triage.*

**Triaged 2026-10-07: enhancement, ready-for-agent.** The facts this file
left unchecked are checked:

- Microsoft, `StartServiceCtrlDispatcher`: "When the service control manager
  starts a service process, it waits for the process to call the
  StartServiceCtrlDispatcher function … (within 30 seconds)"; outside the SCM
  the call fails with `ERROR_FAILED_SERVICE_CONTROLLER_CONNECT`. Neither
  binary calls it, so neither can be registered with `sc.exe create` today.
- NSSM stops a wrapped process with Ctrl+C, then `WM_CLOSE`, then `WM_QUIT`,
  then `TerminateProcess`, "1500 milliseconds" apart by default. The Ctrl+C
  handler catches the first, and a daemon still draining ~4.5 s later is
  killed. A wrapper works only with its timeouts raised.
- `windows-service` 0.8.1 depends on `bitflags` ^2.3, `widestring` ^1 and
  `windows-sys` ^0.61. `bitflags` 2.13 and `windows-sys` 0.61.2 are already in
  `Cargo.lock`: +2 packages, Windows-only, and the `unsafe` stays inside the
  crate. Direct `windows-sys` would be the tree's first production `unsafe`.

**Category:** enhancement
**Summary:** both daemons can run under the Windows Service Control Manager:
started, stopped gracefully, reloaded, and logging to a file.

**Desired behavior:**

- `--service NAME` (Windows only; refused elsewhere) makes the process call
  the dispatcher through `windows-service` and run as service `NAME`.
  Without it the binary is a console process, as today: no dispatcher
  attempt, no auto-detection.
- STOP and PRESHUTDOWN start the same graceful shutdown the console handlers
  start (`rdns::shutdown`). The service reports STOP_PENDING with wait hints
  covering the existing drain budget, then STOPPED with the process's exit
  code, so a failed start shows as a failure in the SCM. No new timeout.
- PARAMCHANGE (`sc.exe control NAME paramchange`) triggers exactly what
  SIGHUP triggers on Unix — Windows' first reload path, independent of #188.
- `--log-file PATH`, on both daemons and every platform (`log-file` in
  `[server]`): log lines go to that file instead of standard error, appended,
  and reopened on reload so external rotation works. The file's lines carry a
  UTC timestamp: `rdns_transport::logging::init` omits them on purpose
  because journald stamps standard error, and nothing stamps a file. One
  init, shared by both daemons, still. ~~Under `--service` it is
  required~~ Under `--service` a log destination is required — `--log-file`,
  or `--event-log` once #192 lands (amended triaging #192): a service with
  no log destination is refused at startup (§4 — standard error goes nowhere
  there).
- All new flags are checked before `--check-config` returns (§15).
- `docs/spec/06` gains the recipe: `sc.exe create NAME binPath= "…\rdnsd.exe
  --service NAME --config …" start= auto`, `sc.exe start|stop|delete`, and
  `sc.exe control NAME paramchange` for reload. No installer subcommand.

**Acceptance criteria:**

- [ ] Windows: a service created with `sc.exe create` starts, answers
      queries, and reports RUNNING.
- [ ] `sc.exe stop` during an AXFR: the transfer completes, the service
      reports STOP_PENDING then STOPPED, exit code 0.
- [ ] A start that fails (bad zone file): the service reports STOPPED with a
      non-zero exit code, and the reason is in the log file.
- [ ] `sc.exe control NAME paramchange` reloads a changed zone file.
- [ ] `--service` with no log destination is refused; `--service` on Linux is
      refused; both also under `--check-config`.
- [ ] `--log-file` lines carry timestamps; standard-error lines still do not.
- [ ] `--log-file` on Linux writes there and not to standard error, and
      reopens after the file is moved and SIGHUP sent.
- [ ] A console run without `--service` behaves exactly as today.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit; the service code is
      Windows-only, so the Windows run is the one that compiles it (§1).
- [ ] `cargo deny` (or the tree's license check) passes with the two new
      packages.

**Out of scope:**

- The Windows Event Log as a sink (#192).
- An install or uninstall subcommand.
- Log rotation inside the daemon.
- `SERVICE_WIN32_SHARE_PROCESS`.
