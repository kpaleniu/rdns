### 180. KSK rollover is open-loop: nothing checks the parent's DS before a key is retired — **filed 2026-10-05**, **enhancement**, **ready-for-agent**

#44f automated ZSK rollover with four timing fields, and #55 publishes
CDS/CDNSKEY inside each key's `SyncPublish`/`SyncDelete` window
(`rdns/src/zone_signer.rs:860-930`, `KeyTiming` at
`rdns/src/dnssec_key.rs:142-170`). The KSK's `Inactive` and `Delete` are
still timestamps the operator writes. If the parent has not picked up the CDS
by then, the zone goes bogus at every validator.

`docs/spec/04-dnssec.md:140` says "withdraw the old one after the parent has
switched"; nothing checks that it has. `docs/closed/055.md` calls the parent's
behaviour "not checkable from here against a real parent". Searched
`parental`, `checkds`, `ksk.submission`: the `parent` hits are validator code
and comments. Acknowledged, never decided.

Peers: BIND `dnssec-policy` with `parental-agents` queries the DS during KSK
and CSK rolls; Knot's `submission.parent` with `check-interval` and
`parent-delay` holds the roll until the DS appears. PowerDNS Auth does not.

The shape both take is a gate on a step, not a new timer: the KSK's retirement
waits on an observed DS.

## Agent brief

> *This was generated by AI during triage.*

**Triaged 2026-10-06: enhancement, ready-for-agent.** Term in `CONTEXT.md`:
**Parental agent**.

**Category:** enhancement
**Summary:** hold a key-signing key's retirement until the parent's DS
RRset, asked of operator-named parental agents, shows its successor.

**Current behavior:** `KeyTiming` is absolute timestamps the operator
writes; each signing run compares them with now. A KSK's `Inactive` (stops
signing the DNSKEY RRset) and `Delete` (leaves it) happen on time whether or
not the parent has published a DS for the successor. If it has not, every
validator sees the zone as bogus. `docs/spec/04` tells the operator to
withdraw the old key "after the parent has switched"; nothing checks.
`rdnsd` never asks anyone for a DS.

**Desired behavior:**

- The gate applies to SEP keys only (`is_sep()`: KSKs and CSKs). ZSKs
  retire on their timestamps as now.
- A SEP key past its `Inactive` or `Delete` time keeps signing and stays
  published until both hold:
  1. every parental agent's DS RRset contains a DS matching another SEP
     key that is active and is not itself retiring;
  2. that has been continuously true for at least the TTL of the DS RRset
     as the agents return it — validators may hold the old DS that long
     (RFC 7583's DS propagation).
  This is Knot's condition (`submission.parent`, `parent-delay`); BIND's
  `parental-agents` is the same gate.
- Parental agents: `--parental-agent ZONE@ENDPOINT`, repeatable, and
  `parental-agents = [...]` in `[zones.*]`. `ENDPOINT` is `rdns::endpoint`'s
  syntax, so `#key` (TSIG) and `+tls=name` work as for `--secondary` (§7).
  Refused at startup, before `--check-config` returns: a zone that is not
  served, a zone that is not signed, an unparseable endpoint.
- Every agent must agree. One unreachable, or one disagreeing, holds the
  key: a stale anycast parent node must not have the key pulled from under
  it.
- Unknown is hold: after startup, nothing retires until the first check
  has answered. DS state lives in memory; a restart re-checks.
- Checked hourly (Knot's `check-interval` default; a constant), and only
  while some SEP key is inside its sync window or past an `Inactive` or
  `Delete` time. Otherwise no queries go out.
- DS answers are not validated (`rdnsd` has no validator, and the operator
  chose the agents). `--help` and `docs/spec/04` say to use `#key` or
  `+tls=` for an agent reached across an untrusted path: a forged DS answer
  can make a key retire early, which is the outage this gate exists to stop.
- No parental agents for a zone with SEP keys carrying `Inactive` or
  `Delete`: today's behaviour, plus a warning at startup and at each
  retirement step naming the key. Not a refusal: that would stop every
  existing signed deployment at upgrade (§16).
- Holding is visible: a log line once per held key with the reason (which
  agent, what it returned), and `rdnsctl status` lists held keys.
- `docs/spec/04`'s KSK paragraph describes the gate and the warning.

**Acceptance criteria:**

- [ ] Mock parental agent returning only the old KSK's DS: past the old
      KSK's `Inactive` and `Delete`, it still signs the DNSKEY RRset and is
      still published; the hold is logged once.
- [ ] The agent starts returning the successor's DS with TTL 3600: the old
      KSK retires no earlier than 3600 s later (paused clock), then does.
- [ ] Two agents, one stale: held. Both current: proceeds after the TTL.
- [ ] An agent that times out: held.
- [ ] Restart while held: still held until the first check answers.
- [ ] A ZSK past its timestamps retires on time with agents configured.
- [ ] No agents: retirement on timestamps, with the warnings.
- [ ] No DS query is sent while no SEP key is in a window or past a time.
- [ ] A TSIG-keyed agent is queried with TSIG and its reply verified.
- [ ] Every signed DNSKEY RRset produced during a held roll verifies with
      `verify_rrset` and with dnspython (§1).
- [ ] The startup refusals, also under `--check-config`.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit.

**Out of scope:**

- Removing CDS/CDNSKEY automatically once the DS appears (`SyncDelete`
  stays a timestamp).
- Finding parent servers by resolution.
- Validating the parent's DS RRset.
- Gating ZSK steps, or the new KSK's activation.
