### 192. No Windows Event Log sink — **filed 2026-10-07**, **enhancement**, **ready-for-agent**

Split from #190, which gives both daemons `--log-file` so a Windows service
logs somewhere. Operators who run Windows Server watch the Event Log, not
files, and a log sink there is what they expect of a service.

Today both daemons log through one shared init,
`rdns_transport::logging::init`, to standard error with no timestamps
(journald adds them); #190 adds a timestamped file. Nothing writes to the
Event Log.

Not checked, and each needs checking before a remedy is named (`CLAUDE.md`
§18, §19): which crate provides a `tracing` layer for the Event Log, and what
it adds to `Cargo.lock`; whether an event source must be registered in the
registry first (an administrator step at install time) and what happens to
events written without one; whether a message-table resource is needed for
events to render without "the description for Event ID … cannot be found";
how `tracing` levels map to Event Log types; whether the sink runs alongside
the file or instead of it.

**Triaged 2026-10-07: enhancement, ready-for-agent.** Wanted by the owner for
Windows Server operators, who watch the Event Log rather than files.

**Category:** enhancement
**Summary:** `--event-log SOURCE` sends WARN and above to the Windows Event
Log, with descriptions that render, from a source the binary registers
itself.

**What was checked:**

- Microsoft, `RegisterEventSource`: "If the source name cannot be found, the
  event logging service uses the Application log. Although events will be
  reported, the events will not include descriptions because there are no
  message and category message files". An unregistered source is a sink that
  looks as if it works.
- `tracing-layer-win-eventlog` 1.0.1 (MIT): a `tracing` layer; its README has
  the source "created first" with `New-EventLog` as Administrator; no message
  resource mentioned. Depends on `windows` ^0.61.
- `eventlog` 0.4.0 (MIT OR Apache-2.0): a `log` backend; register and
  unregister helpers; "Embeds a small (120-byte) message resource library";
  Error, Warning, then Informational for the rest. Depends on `windows` ^0.58
  and `windows-registry`.
- `Cargo.lock` holds no `windows` crate — only `windows-sys`, its target
  shims and `windows-link` — so either adds a subtree. Not counted.

**Desired behavior:**

- **Build both shapes first** (`CLAUDE.md` §19): (a) the layer plus a
  message resource of our own, (b) `eventlog` behind `tracing`'s `log`
  bridge, structured fields flattened into the text. For each, record the
  packages it adds (`cargo tree -e normal --target x86_64-pc-windows-msvc`,
  before and after) and whether Event Viewer shows each event's text with no
  "description … cannot be found". Keep the lighter one that renders; the
  numbers go in the commit message. If neither renders cleanly, stop and
  report rather than writing an `unsafe` `ReportEventW` layer over
  `windows-sys`.
- `--event-log SOURCE` (`event-log` in `[server]`), Windows only, refused
  elsewhere. Alongside `--log-file`, not instead: the Event Log gets WARN and
  above, the file everything at the configured level. One init for both
  daemons, as `rdns_transport::logging::init` is now.
- Under `--service` (#190), either `--log-file` or `--event-log` satisfies
  the log-destination requirement; #190's brief is amended to say so.
- `--register-event-source NAME` writes the registry entry for `NAME` under
  the Application log with this binary as its message file, then exits;
  `--unregister-event-source NAME` removes it. Both need administrator
  rights and say so on failure. This reverses #190's "no installer
  subcommand" for this step only: the message-file path must be this exact
  binary, which a documented `reg.exe` line gets wrong after an upgrade moves
  it.
- At startup, `--event-log NAME` with no registry entry for `NAME` is refused,
  naming `--register-event-source` (§4). Checked before `--check-config`
  returns (§15).
- `docs/spec/06` gains the Windows recipe beside #190's.

**Acceptance criteria:**

- [ ] The commit message records both shapes' added package counts and the
      rendering result, and says which was kept and why.
- [ ] Windows: after `--register-event-source rdnsd-test`, a WARN logged by
      `rdnsd --event-log rdnsd-test` appears in the Application log under
      that source, with its text shown and no "cannot be found".
- [ ] An INFO line goes to the file and not to the Event Log.
- [ ] `--event-log` with an unregistered source is refused, also under
      `--check-config`; on Linux, `--event-log` is refused.
- [ ] `--unregister-event-source` removes the entry; a second run says it is
      already absent rather than failing silently.
- [ ] `--service` with `--event-log` and no `--log-file` starts.
- [ ] `cargo deny` passes with the added packages.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit; the Event Log code
      compiles only on Windows (§1).

**Out of scope:**

- ETW (`win_etw_tracing`).
- A custom event log (not Application), and event categories.
- Event IDs beyond the level mapping.
