### 189. `rdnsr` cannot ask its upstreams for NSID — **filed 2026-10-06**, **needs-triage**

Found triaging #179, which is the other direction: answering NSID. RFC 5001
§2.1 makes the two independent: "if the resolver side of the recursive name
server wishes to receive identifying information, it is free to add NSID
requests in its own queries, but that is a separate matter."

What it would buy: when an anycast authority or forwarder hands back a bad
answer — a stale zone, a broken signature — the log would name the instance,
not only the shared address. Today `rdnsr` sees the address alone.

Peers, checked in their reference documentation on 2026-10-06:

- BIND `request-nsid`, default `no`: "an empty EDNS(0) NSID (Name Server
  Identifier) option is sent with all queries to authoritative name servers
  during iterative resolution. If the authoritative server returns an NSID
  option in its response, then its contents are logged in the `nsid`
  category at level `info`."
- Unbound: `nsid:` answers only; no outbound option in `unbound.conf(5)`.
- PowerDNS Recursor: `server-id` answers only; no outbound option in its
  settings table.
- Knot Resolver: not checked.

Searched: `build_query` (`rdns/src/resolver.rs`) sends an OPT with payload
size and DO, and no options. No remedy filed beyond what BIND does; whether
the identifier goes to the log, to dnstap, or both is triage's call.
