### 187. No response is padded when the query asked for it (RFC 7830 §4 MUST) — **filed 2026-10-06**, **bug**, **ready-for-agent**

Found triaging #175. RFC 7830 §4 (Standards Track): "Responders MUST pad
DNS responses when the respective DNS query included the 'Padding' option,
unless doing so would violate the maximum UDP payload size." RFC 8467 §4.1(2)
repeats the MUST and recommends blocks of 468 octets.

~~Neither daemon does, on any transport.~~ Neither daemon does on DoT, DoH or
DoQ, which is the violation. On UDP and plain TCP not padding is *required*:
RFC 7830 §6, "implementations MUST NOT use this option if the DNS transport
is not encrypted", because padding "may make DNS amplification attacks
easier". Filed from §4 without reading §6. Every reply's OPT is built by
`ClientEdns::mirror` / `mirror_with` (`rdns-core/src/response.rs`), and
`ClientEdns` records only whether the client sent an OPT and its DO bit — a
query's option 12 is never read. Checked: no code in the tree builds or
recognises the Padding option (`rg -i padding` finds only RSA signature
padding and test fixtures).

One site builds every mirrored OPT, so the change is likely one place; that
is a reading of `mirror`'s doc comment ("Every such reply goes through
here"), not a measurement of the callers. ~~Which transports to pad beyond the
MUST — RFC 7830 makes padding without a request a MAY — is triage's call.~~
§6 settles the transports; triage settled the MAY (below).

> *This was generated by AI during triage.*

**Triaged 2026-10-06: bug, ready-for-agent.**

**Category:** bug
**Summary:** on DoT, DoH and DoQ, pad a response to the next multiple of 468
octets when the query carried an EDNS Padding option; never pad on UDP or
plain TCP.

**Current behavior:** a query's Padding option (code 12) is never read.
`ClientEdns` records only whether an OPT was sent and its DO bit, and every
reply's OPT is built by `ClientEdns::mirror` / `mirror_with`. Nothing in the
tree builds the option.

**What the RFCs require**, quoted:

- RFC 7830 §4: "Responders MUST pad DNS responses when the respective DNS
  query included the 'Padding' option, unless doing so would violate the
  maximum UDP payload size", and "padded DNS messages MUST NOT exceed the
  number of octets specified in the Requestor's Payload Size field".
- RFC 7830 §6: "implementations MUST NOT use this option if the DNS
  transport is not encrypted".
- RFC 7830 §3: the option occurs "at most, once per OPT"; "The PADDING
  octets SHOULD be set to 0x00"; received padding of any value MUST be
  accepted.
- RFC 8467 §4.1(2): the server "SHOULD pad the corresponding response to a
  multiple of 468 octets". Unbound does exactly this (`pad-responses`,
  `pad-responses-block-size: 468`, "Only responses to padded queries will be
  padded").

**Desired behavior:**

- `ClientEdns` records that the client sent Padding, as one field among the
  per-option fields #179 (NSID) also needs; whichever lands first builds
  that shape, the other adds a field.
- Padding is added at serialization, because only the final length decides
  it. The reply builder knows the transport: DoT, DoH and DoQ pad; UDP and
  plain TCP never do, whatever the client sent (§6), and echo no Padding
  option.
- Size: the whole message, the option's 4-octet header included, rounded up
  to the next multiple of 468, but never past the client's advertised payload
  size; where the next block would overshoot, pad to the limit instead.
  Octets are 0x00.
- Unasked responses are not padded (§4's MAY, declined).
- Every message of a multi-message response (AXFR or IXFR over a TLS
  connection) is padded. Padding is computed before TSIG signs the message,
  so the MAC covers it; the TSIG record then leaves the total off-block by
  its own length, which is accepted.
- No flag: it is a MUST.

**Acceptance criteria:**

- [ ] DoT, DoH and DoQ, both daemons: a query with an empty Padding option
      gets a reply whose length is a multiple of 468, with one Padding
      option of 0x00 octets.
- [ ] The same query without Padding: no Padding option, length unchanged
      from today.
- [ ] UDP and plain TCP with Padding: no Padding option in the reply.
- [ ] A client payload size of 512 with a reply of 500 octets: padded to at
      most 512, not 936.
- [ ] A query whose Padding option carries non-zero octets is accepted and
      answered.
- [ ] An AXFR over DoT with Padding and TSIG: every message carries Padding
      and every MAC verifies (dnspython, §1).
- [ ] dnspython reads the padded replies (`dns.edns.Option` code 12).
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit.

**Out of scope:**

- Padding unasked responses.
- Query padding upstream (#175 does it for `rdnsr`'s DoT).
- A configurable block size.
