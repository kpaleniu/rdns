### 195. Concurrent dynamic UPDATEs lose acknowledged changes — **filed 2026-10-08**, **bug**, **ready-for-agent**

Found in review. `answer_update` takes the served-zone snapshot `previous`
(`rdnsd/src/dispatch.rs:1336`) before the `applying` lock that is meant to
serialize RFC 2136 §3.7's read-modify-write (`:1448`). With no signing
configured, `apply_update_to_file` then sees the file digest match the last
write and reuses `previous` as the source (`:1770`):

```rust
let reused = known == Some(digest) && check.signing.is_none();
```

so an UPDATE that queued behind another applies its change to the version
before that one and writes the result back. Both clients get NOERROR; the
earlier change is gone from the file and from the served zone.

Measured with a throwaway test on the `spawn_updatable` fixture: 16 UPDATEs
sent concurrently over TCP, each adding a distinct `hN.example.com. A`, then
the file read back. Windows, debug build.

```
NOERROR replies: 16/16; names in file: 1/16
```

Re-taking the snapshot immediately after the lock is acquired gave `16/16`.
That is a check of the diagnosis, not a proposed fix: whether the snapshot
should move, or the lock should cover the NOTAUTH check too, is open. The
probe, to become the regression test:

```rust
#[tokio::test(flavor = "multi_thread", worker_threads = 8)]
async fn concurrent_updates_are_not_lost() {
    let dir = ScratchDir::new("concurrent-updates");
    let key = update_key(rdns::tsig::UpdatePolicy::Any);
    let addr = spawn_updatable(dir.path(), key.clone()).await;
    const N: usize = 16;
    let mut tasks = tokio::task::JoinSet::new();
    for i in 0..N {
        let key = key.clone();
        tasks.spawn(async move {
            let message = update_message(
                "example.com.",
                vec![a_record(&format!("h{i}.example.com."), "192.0.2.50")],
            );
            let bytes = message.to_bytes_within(4096).expect("serialize");
            let signed = rdns::tsig::sign_request(bytes, &key, tsig::now()).expect("sign");
            round_trip(addr, signed).await.rcode
        });
    }
    let mut ok = 0;
    while let Some(r) = tasks.join_next().await {
        if r.unwrap() == ResponseCode::Ok { ok += 1; }
    }
    let written = std::fs::read_to_string(dir.join("example.com.zone")).expect("read back");
    let present = (0..N).filter(|i| written.contains(&format!("h{i}.example.com."))).count();
    assert_eq!(present, ok, "every acknowledged UPDATE reached the file");
}
```

One client is enough to hit it: messages on one TCP connection are answered
concurrently (`rdns-transport/src/tcp.rs`, RFC 7766 §6.2.1.1).

#### 195a. A SIGHUP reload is not serialized with an UPDATE

By reading; not reproduced. Nothing on the reload path takes `applying`.
`install_all_zones` (`rdnsd/src/zones.rs`) re-plans its diff if the map's
generation moved, but installs the zones it read regardless. A reload that
read the files before an UPDATE wrote, and installs after the UPDATE
installed, puts the pre-UPDATE zone back in service. The file still has the
change, and the `applying` digest still says "this is what we last wrote", so
the next unsigned UPDATE takes the `reused` path above against the reverted
copy and writes the earlier change out of the file too.

~~Unix only: SIGHUP has no trigger on Windows.~~ **Wrong:** `reload_once`
(`rdnsd/src/main.rs:1463`) is what SIGHUP, `rdnsctl reload` and the
re-signing timer all call, so all three platforms hit it. The claim generalized
from the trigger to the operation.

#### 195b. Signed zones sign incrementally against the stale snapshot

Folded into 195 in triage: the fix that takes the served version under the
lock removes it. Closes with 195.

By reading; not measured. With signing configured, `reused` is false and the
file is re-parsed, so the data is right. `sign_one_incrementally(previous,
zone)` (`rdnsd/src/dispatch.rs:1827`) still takes the stale `previous` as the
version to carry signatures forward from and to bump the served serial from.
~~What that does to the served serial and to the IXFR delta is unknown.~~
**The serial is safe:** it is `signed_serial(file_serial, signed_at)`
(`rdns/src/zone_signer.rs:258`), taken from the re-parsed file and not
from `previous`. What is left is which signatures carry forward, and
`FreshlySigned::verify` runs on the result before it is installed. Not
measured.

Instances: `install_zone`'s three non-test callers (`dispatch.rs` UPDATE,
`main.rs` startup catalog, `replication.rs` transfer) and `install_all_zones`.
Only the UPDATE path reads a snapshot and writes back from it; replicated
zones refuse UPDATE. Not checked: the catalog generator's rebuild on reload
against a concurrent UPDATE.

## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Make UPDATE and reload one serialized writer of served versions,
so no acknowledged UPDATE is lost.

Terms are `CONTEXT.md`'s: **zone file** (the operator's text, where an UPDATE
is written back) and **served version** (what `rdnsd` answers from).

**Current behavior:**
- `answer_update` reads the served version before taking the lock that
  serializes RFC 2136 §3.7's read-modify-write. An UPDATE queued behind
  another holds a served version that predates it. With no signing, the
  file-digest shortcut in `apply_update_to_file` then uses that stale copy as
  its base and writes it back: the earlier change is gone from the zone file
  and the served version, and both clients got NOERROR. Measured 1/16 changes
  surviving 16 concurrent UPDATEs.
- `reload_once` (SIGHUP, `rdnsctl reload`, the re-signing timer) takes no part
  in that lock. A reload that reads zone files before an UPDATE writes and
  installs after it reverts the served version; the next unsigned UPDATE then
  writes the change out of the zone file too (195a).
- The lock's doc comment justifies one lock for all zones with "two
  concurrent UPDATEs is not a workload this has". The probe refutes it.

**Desired behavior:**
- One lock serializes every replacement of a served version from its zone
  file: each UPDATE, and each reload from before it reads the first zone file
  until it has installed. It is one lock for all zones.
- It lives beside `install_zone`/`install_all_zones`, named for what it
  guards (e.g. `ZoneWrites`), not on `UpdateHandling`; the per-path
  `FileDigest` map of what this server last wrote moves with it. Lock order
  everywhere: this lock, then `zone_map`.
- An UPDATE takes its served version *under* the lock.
- The file-digest shortcut stays (#64b): with the snapshot under the lock,
  "the last zone file written is the last served version installed" holds.
- The doc comment states the actual reason for one global lock: a reload
  replaces every zone at once. The workload claim goes.

**Key interfaces:**
- `UpdateHandling::applying`: replaced by the shared lock; `UpdateHandling`
  holds a handle to it.
- `reload_once` / `ReloadContext`: take the same lock.
- `apply_update_to_file`'s `previous` and `known` arguments: both must come
  from under the lock.

**Acceptance criteria:**
- [ ] A deterministic test holds the lock, sends two UPDATEs adding distinct
      names so both are waiting on it, releases it, and asserts both names are
      in the zone file and answered by the server. Shown failing against the
      current code.
- [ ] A deterministic test holds the lock, starts a reload through the
      control trigger and sends an UPDATE, releases it, and asserts the
      UPDATE's change is in the zone file and answered after both finish.
      Shown failing against the current code.
- [ ] The commit message says which tests failed before the fix and how.
- [ ] `cargo test --workspace` and `cargo clippy --workspace --all-targets`
      clean on Windows and on Linux, with the platform of each run stated.
- [ ] `cargo fmt --all --check` and `cargo doc --workspace --no-deps` clean.
- [ ] 195 moved to `docs/closed/` with a closing note covering 195a and 195b,
      and its `TODO.md` row added.

**Out of scope:**
- One lock per zone. If parallel UPDATEs to different zones matter, that is
  a new number.
- #198 (the journal is written under the `zone_map` write guard).
- Changing what the digest shortcut decides, or the incremental signer.
- Transfers into replicated zones: those refuse UPDATE.
