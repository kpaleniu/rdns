### 188. Neither daemon can be controlled or reloaded on Windows — **filed 2026-10-06**, **bug**, **ready-for-agent**

Found triaging #178. On Windows `--control-socket` is refused at startup in
`rdnsd` (and, after #178, `rdnsr`), and `rdns::shutdown::reload_signal`
returns `None` because there is no SIGHUP. So nothing an operator does can
make a running daemon re-read anything there: `rdnsd`'s zones reload only on
its re-signing timer; `rdnsr`'s TLS certificate and RPZ files never, and
after #174 and #176 its local zones and NTA file never.

**How it was missed.** The control socket came in with `652e4d5`
(2026-08-01). `rdnsd/src/control.rs` gave the reason as "neither `std` nor
`tokio` exposes AF_UNIX on Windows", and `docs/spec/03` §3.9 as "`tokio` has
no `UnixListener` on Windows". Both are true, and both were taken as settling
the question. Nobody asked which transport would work on Windows. `tokio`
1.53.1, the version in `Cargo.lock`, ships `tokio::net::windows::named_pipe`.
The consequence for reload was never written down anywhere. Both statements
are corrected in place, pointing here.

**No remedy filed** (`CLAUDE.md` §18): a named pipe with an owner-only
security descriptor is one candidate. AF_UNIX through the OS rather than
`std`/`tokio` is another. Neither has been built or measured. Triage decides
which, and what the Windows equivalent of mode 0600 is.

## Agent brief

> *This was generated by AI during triage.*

**Triaged 2026-10-07: bug, ready-for-agent.** Windows is a deployment target:
the tree already carries Windows stop handlers (`ctrl_break`, `ctrl_close`,
`ctrl_shutdown` in `rdns::shutdown`), ADR 0006's dual-stack bind, and a
Windows CI leg. A daemon there can never be made to reload.

**Category:** bug
**Summary:** a named-pipe control channel on Windows behind the same
`--control-socket` flag and the same line protocol, so `rdnsctl` works and
`reload` exists there.

**Current behavior:** `--control-socket` is refused on Windows, and
`reload_signal()` is `None` there (no SIGHUP). `rdnsd` reloads only on its
re-signing timer; `rdnsr` never re-reads its certificate or RPZ files.

**Why a named pipe, with the default security descriptor:** Microsoft's
"Named Pipe Security and Access Rights": "The ACLs in the default security
descriptor for a named pipe grant full control to the LocalSystem account,
administrators, and the creator owner. They also grant read access to members
of the Everyone group and the anonymous account." Sending a command needs
write access, so the default already limits control to the daemon's account,
administrators and SYSTEM. A custom descriptor would need tokio's `unsafe`
`create_with_security_attributes_raw`, and the tree has no `unsafe` outside
test allocators. Rejected: loopback TCP with a key or TLS (BIND, Unbound) —
authentication, a key file and a port; AF_UNIX via `windows-sys` — `unsafe`
and file ACLs.

**Desired behavior:**

- On Windows, `--control-socket` takes a pipe name and nothing else: a
  value not starting `\\.\pipe\` is refused at startup, before
  `--check-config` returns, saying what was expected. On Unix, unchanged.
- The server end: `tokio::net::windows::named_pipe::ServerOptions` with
  `first_pipe_instance(true)` — a name already taken is a startup failure,
  the pipe form of the socket's "refuse rather than steal" — and
  `reject_remote_clients(true)` (tokio's default; set it explicitly). One
  pipe instance per waiting client, then the same one-command conversation
  and read timeout as the socket.
- It sits behind the shared transport #178 introduces: accept, then one
  conversation. If #188 lands first, it moves the socket half out of `rdnsd`
  itself, for `rdnsd` alone; #178 then adds `rdnsr`.
- `rdnsctl` on Windows: opens the pipe as a file with `std` (no tokio), and
  defaults to `\\.\pipe\rdnsd`; `-s` as on Unix. Exit codes unchanged.
- Every command `rdnsd` answers on Unix answers on Windows, `reload`
  included.
- `docs/spec/03` §3.9 describes both transports; its struck Unix-only line
  already points here. `rdnsctl`'s and `rdnsd/src/control.rs`'s headers are
  updated to match.

**Acceptance criteria:**

- [ ] Windows: `rdnsd --control-socket \\.\pipe\rdnsd-test` answers
      `status`, `reload` and `dump` through `rdnsctl -s`.
- [ ] `reload` on Windows re-reads a changed zone file and reports it.
- [ ] A second `rdnsd` given the same pipe name refuses to start.
- [ ] `--control-socket C:\some\path` on Windows is refused at startup, also
      under `--check-config`.
- [ ] A process connecting with read access only cannot get a command
      answered (assert the server sees no command line).
- [ ] Unix behaviour and tests unchanged.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      **both** Windows and Linux, platforms named in the commit — the code is
      `cfg`-split both ways now (§1).

**Out of scope:**

- Running as a Windows service (#190).
- A custom security descriptor, or groups beyond the default's.
- A TCP control channel on any platform.
