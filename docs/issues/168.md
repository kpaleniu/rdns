### 168. A resolution has no deadline: one `resolve` can take 157.5 s — **filed 2026-10-04**, **bug**, **needs-triage**

Found grilling #166. Nothing bounds a whole resolution. Each exchange is bounded
at `timeout_ms / 2` (`recurse.rs`'s `exchange_timeout`, 2.5 s at the default
5000), and `ask_any` tries every server of a delegation in turn, spending one of
`query_budget`'s 64 per try. The budget is a count of queries, not of time.

Measured with a throwaway paused-clock probe, reverted: `Resolver::resolve` in
recursive mode, default `ResolverConfig`, a root answering with a referral to
`example.test.` whose glued nameservers never answer.

| nameservers | elapsed |
|---|---|
| 1 | 2.5 s |
| 4 | 10 s |
| 13 | 32.5 s |
| 70 | 157.5 s (63 × 2.5 s: the budget, less the root's) |

Four silent nameservers already reach `--connection-idle-timeout`'s default
10 s. A UDP client has retried or given up long before, so the answer is
computed for nobody. Measured on the
resolver alone, not through `rdnsr`'s `handle_query`; `--serve-stale-first`
answers from cache ahead of a refresh and was not part of it.

How the transports bound a slow handler differs: TCP waits for it however long
it takes (`tcp.rs`'s writer drains after the read loop ends); DoQ and DoH close
an idle connection with the answer still in flight one `idle_timeout` later,
so a lone slow query gets about twice the idle timeout (`quic.rs`'s
`serve_connection`, `https.rs`'s `until_idle`). A deadline below the idle
timeout would make the difference moot.

No remedy costed. A deadline value wants checking against BIND's
`resolver-query-timeout` and Unbound before one is chosen (`CLAUDE.md` §4).
