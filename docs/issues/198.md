### 198. The IXFR journal is written and fsynced under the zone map's write guard — **filed 2026-10-08**, **bug**, **ready-for-agent**

Found while checking #195a. `install_zone` and `install_all_zones`
(`rdnsd/src/zones.rs:250`, `:316`) take `zone_map.write()` and then call
`journal.save`, which renders the zone's whole delta log as text
("Regenerated whole on every change") and goes through
`persist::write_atomically`, which calls `sync_all`. That is blocking file
I/O on a runtime worker, with the write guard every query's read guard waits
on held for its duration — §9 forbids both.

The comment there states the reason: the journal is the delta log on disk,
and saving it under the same guard that recorded it means a restart never
sees a log and journal that disagree. That argument is about the `deltas`
guard; it does not obviously need the zone map's.

Instances: `journal.save` at `zones.rs:272` and `:336`, both under both
guards; `journal.forget` (`remove_file`) at `:327`, `:385`, `:438`.

Not measured: how long a save takes for a realistic delta log, and so how
long queries stall per UPDATE, reload or transfer with `--journal` set. No
remedy is proposed until that is measured.

## Triage notes (2026-10-09)

> *This was generated by AI during triage.*

Confirmed by reading: `install_zone` and `install_all_zones` call
`journal.save` holding the zone map's write guard and the delta log's
(`rdnsd/src/zones.rs:247`, `:309`); `forget` likewise at `:300`, `:353`,
`:393`. Nothing bounds a delta's size: a re-sign rewrites every RRSIG, so its
step is the whole zone's signatures.

Measured with a throwaway probe (not committed), `Journal::save` alone,
records of RRSIG-like presentation length, Windows, release, best of three:

| journal | save | file |
|---|---|---|
| 32 UPDATE-sized steps of 10 records | 7.8 ms | 175 KB |
| one re-sign step, 10k records each way | 25.6 ms | 3.6 MB |
| one re-sign step, 100k records each way | 235 ms | 36 MB |
| 32 re-sign steps, 10k records each way | 731 ms | 116 MB |

Every query waits that long per UPDATE, reload, re-signing tick or transfer
on a server with a zone directory.

The stated reason for saving under the guard does not hold:
`restore_journals` drops a journal that does not reach the loaded serial
(`journal::usable_against`, `zones.rs:348`), so a journal one step behind
costs at most a full transfer (RFC 1995 §4). What does hold is order: two
writes for one zone must land in order, and transfers install without
`ZoneWrites`.

## Triage decisions (2026-10-09)

- One journal-writer task. Installs and withdrawals queue "persist zone Z" or
  "forget zone Z" and return; the task renders and writes on a blocking
  thread, the newest request per zone winning, so a save and a delete for one
  zone stay in order.
- `DeltaLog` holds `Arc<ZoneDelta>`, so the writer's snapshot is refcounts.
- The writer holds a `Busy` while its queue is non-empty, none while idle.
- A failed write stays a WARN; no counter.
- Startup (`restore_journals`, `discard_orphan_journals`) keeps using the
  journal directly.
- `CONTEXT.md` gains **Delta log** and **Journal**; the journal may lag.
- No ADR: a background writer is cheap to change.

## Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Move journal rendering, writing and deleting off the zone map's
write guard into one ordered writer task.

**Current behavior:** each install renders the zone's whole delta log and
fsyncs it under the zone map's write guard, on a runtime worker; queries wait
for it (7.8 ms per UPDATE to 235 ms per re-sign of a 100k-record zone,
measured above). `CLAUDE.md` §9.

**Desired behavior:**
- No file I/O for the journal under any lock an answer takes, and none on a
  runtime worker.
- One writer task owns every runtime `save` and `forget`. Requests carry the
  zone and, for a save, a snapshot of its steps; the newest request per zone
  replaces an older pending one. Order per zone is the queue's.
- `DeltaLog` stores `Arc<ZoneDelta>`; `all` hands out cheap clones.
- The writer holds a `Busy` while it has work, so the shutdown drain waits
  for pending saves; it holds none while idle (§9).
- A failed write is a WARN, as now.
- `ZoneContext.journal` becomes the writer's handle; `install_zone`,
  `install_all_zones` and the withdraw paths send to it.

**Acceptance criteria:**
- [ ] A test installs a zone through a `ZoneContext` whose writer queue
      nothing drains, asserts no journal file exists and the zone is answered,
      then runs the writer once and asserts the file is there. Shown failing
      against the current code (it writes the file during the install).
- [ ] `an_update_leaves_a_journal_that_survives_the_process` and the other
      journal tests pass, flushing the writer before reading the file.
- [ ] A test that a `forget` queued after a save for the same zone leaves no
      file.
- [ ] The shutdown drain waits for a pending save.
- [ ] The commit message reports the triage probe rerun: the save cost now
      paid off the guard.
- [ ] `cargo test --workspace`, clippy, doc and fmt clean on Windows and
      Linux, platforms stated.

**Out of scope:** the journal's format; bounding a delta's size; a failure
counter; the startup paths.
