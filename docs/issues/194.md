### 194. No Windows installer — **filed 2026-10-07**, **needs-triage**

Split from #190 and #192. Both leave a step to the operator that a Windows
program normally gets from its installer, run once, elevated:

- #190: registering and removing the service. Today `docs/spec/06` gives
  `sc.exe create … binPath= "C:\rdns\rdnsd.exe --service rdnsd --config …"`
  and `sc.exe delete`.
- #192: registering the event source, whose `EventMessageFile` must name the
  installed binary and must follow it when an upgrade moves it. #192 first put
  that in the binary as `--register-event-source`; amended to a hand-written
  `reg.exe` recipe pending this item.

An MSI does both from its own tables (`ServiceInstall`, `ServiceControl`;
WiX's `util:EventSource`), knows the installed path, and undoes both on
uninstall. What stays in the binary regardless: the SCM dispatcher and
control handling (#190, `36f2353`), the message-table resource, and the
startup refusal of an unregistered `--event-log` source (#192).

Prerequisite, measured: there is nothing to install. `.github/workflows/`
holds `ci.yml` alone; no job builds, keeps or publishes a Windows binary, and
no issue asks for one. A release artifact comes first, for every platform,
and may want its own number when this is triaged.

Not checked, and each needs checking before a remedy is named (`CLAUDE.md`
§18, §19): WiX version and its licence terms, and whether `cargo-wix` is
current; whether CI can build an MSI on the Windows leg and what it costs in
minutes; code signing — an unsigned MSI meets SmartScreen — and who holds the
certificate; per-machine install paths for the config and zone files (and
§15's private-file check under them); whether the installer creates and
starts the service or only registers it; upgrade and uninstall behaviour for
a running service, and whether uninstall keeps the config and zones; what
the DNS servers that ship for Windows do.
