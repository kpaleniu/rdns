**Triaged 2026-10-05.**

> *This was generated by AI during triage.*

Reproduced on Linux with a throwaway copy of the test that kept `rdnsd`'s
stderr and exit status: 5 failures in 100 runs of the `startup` binary. In
each, the connect succeeded 84–186 µs after `rdnsd` was spawned — before it
could have bound anything — and the read was reset 50–450 µs later with
`rdnsd` still running and silent. With `--test-threads=1`, 0 failures in 160
runs. A bind of port 0, close and connect, repeated 5000 times with nothing
else running, was refused every time.

The cause, consistent with all of that: the test's throwaway listener is
open while another test thread spawns a child (`rdnsd --check-config`), which
inherits the descriptor until its `exec` — `SOCK_CLOEXEC` closes it only
there. The test drops its own copy and connects; the kernel completes the
handshake from the copy the child still holds; the child execs, that copy
closes, and the queued connection is reset. "The port race" above was the
right neighbourhood: a race on the released port, but with the test's own
listener rather than with another binder. Not observed directly: inserting
an `ss` call to catch the inherited listener took the failure away (0 of 40),
by moving the timing. CI has not run since the test was added.

Only this test releases a port for a child to bind. Not fixable by letting
`rdnsd` pick its own port: it refuses `--port 0`, and changing that is a
product change for a test's sake.

## Agent Brief

**Category:** bug
**Summary:** No child process may be spawned in `rdnsd`'s startup integration
tests while `an_idle_connection_is_closed_after_the_configured_timeout` holds
its throwaway listener.

**Current behavior:**
The test binds `127.0.0.1:0` to learn a free port, drops the listener, and
starts `rdnsd` on that port. Concurrent tests in the same binary spawn
`rdnsd` processes, and a child forked while the listener is open inherits it
until `exec`. A connect in that window is accepted by the inherited listener
and reset when the child execs, failing the test's `Ok(0)` assertion with
`ConnectionReset` roughly 5% of the time on Linux.

**Desired behavior:**
One lock, a `static` mutex in that test binary, is held from the throwaway
bind until the listener is dropped, and every process spawn in the binary
takes the same lock around the spawn itself (not around waiting for the
process). The shared `rdnsd(args)` helper and the test's own spawn both go
through it. The comment on the lock says why: an inherited listener outlives
the drop until the child's `exec`.

**Key interfaces:**
- The test file's `rdnsd(&[&str]) -> Output` helper: spawns under the lock,
  waits outside it.
- The idle-timeout test's port selection: the bind, `local_addr` and drop
  happen under the lock.

**Acceptance criteria:**
- [ ] Watched failing first: 100 runs of `cargo test -p rdnsd --test startup`
      on Linux, default test threads, without the lock, and the failure
      count reported (expect a few).
- [ ] With the lock, 100 such runs and 0 failures.
- [ ] `cargo test --workspace` and `cargo clippy --workspace --all-targets`
      clean on Windows and Linux.
- [ ] The commit message gives both counts and says the cause was inferred
      from timing and the single-threaded runs, not observed.

**Out of scope:**
- `rdnsd` accepting `--port 0`.
- Other test binaries: none releases a port for a child to bind.
