### 210. Zone state as one append-only log per zone, and a reload that can move the serial backwards — **filed 2026-10-10**, **enhancement**, **needs-triage**

`rdnsd` writes the operator's zone file. UPDATE rewrites it whole
(`apply_update_to_file`, `rdnsd/src/dispatch.rs`), the journal is a second
file written after it (`rdnsd/src/journal_writer.rs`), and a secondary's
transfer state is a third (`rdns/src/secondary.rs`). Each is atomic alone
(`rdns-core/src/persist.rs`); none is atomic with another. The settled
decision is `docs/architecture/persistence.md` ("plain files, no database");
#64c measured and declined making the file a checkpoint.

## Reproduced (Windows, 9ec19c6 plus uncommitted test-only changes)

`rdnsd --zone-dir Z --control-socket P --tsig-key
hmac-sha256:upd.key:S:*:example.test.`, a zone at serial 1:

1. Read the zone file into a buffer and add `mail IN A 192.0.2.25` to it: an
   editor holding the file open.
2. dnspython sends a TSIG-signed UPDATE adding `dyn A 198.51.100.7`: NOERROR,
   `dyn` served, written into the file, serial 2.
3. Write the buffer over the file; `rdnsctl --socket P reload`: exit 0,
   "reloaded 1 zone(s)".

Result: `dyn` is gone from the file and from answers; `mail` is served; the
served serial is **1**. The log says "loaded zone" and "zones reloaded",
nothing more.

- The UPDATE was acknowledged and lost.
- The serial went backwards. A secondary at 2 sees 1 as older (RFC 1982
  §3.2) and keeps `dyn` without `mail`. Reasoned, not run against a
  secondary.

The second needs no UPDATE: any reload of a file whose serial is below the
served one does it (a restored backup, a `git checkout`). `apply_update_to_file`'s
digest protects an edit made before an UPDATE, not an editor buffer loaded
before one. The likeliest real trigger is an ACME DNS-01 client writing
`_acme-challenge` TXT into a hand-edited zone.

## Not verified

- A signed zone's served serial is `file serial + hours since the epoch`
  (`rdns::zone_signer::signed_serial`). A restart within the same hour
  re-signs at the same serial, and `rdns::journal::usable_against` compares
  serials only, so the journal is kept against different content. Whether
  the next IXFR then breaks a secondary or only costs an AXFR: not tried.
- `Journal::save` with an empty history and `Journal::forget` drop
  `remove_file`'s error (`let _ =`) without a stated reason (`CLAUDE.md` §4).

## The design proposed

One file per zone holding a snapshot then deltas; the operator's zone file is
input only:

- Each change (UPDATE, transfer, re-sign, reload) is one checksummed delta,
  appended and fsynced before it is acknowledged. Load replays the snapshot
  and deltas and stops at the first bad checksum.
- Compaction writes a new snapshot plus the IXFR window and renames it over
  the log (`persist::write_atomically`).
- A reload is a three-way merge: `diff(last import, file now)` applied to the
  served zone, as Knot's `zonefile-load: difference`. A record added by
  UPDATE is in neither side of that diff and survives.
- The served serial comes from the log: every delta, re-signs included, is
  the next serial, so it cannot go backwards or name two contents.
- Lease and transfer state can ride on the log entries rather than a sidecar
  file.
- The query path is unchanged: memory only.

What it removes: the re-read and digest in `apply_update_to_file`, the
whole-file rewrite per UPDATE (387 ms of 1 335 at a million records, #64),
the zone/journal ordering and `usable_against`'s discard, the separate
transfer-state file. What it costs: a recovery path (replay, compaction,
torn-tail handling) that runs only after a crash; the file no longer shows the
whole zone (`rdnsctl export`); a rule for an operator edit and an UPDATE on
the same RRset; a migration from today's files.

The smaller alternative fixes only the serial: a reload refuses, or warns
on, a served serial that does not move forward; `rdnsctl freeze`/`thaw` as
BIND's `rndc`. That leaves the UPDATE-lost case to operator discipline.

## References for triage

Compare against, and quote (`CLAUDE.md` §4), each of these on four questions:
how a torn write is detected, when fsync happens, how compaction is made
atomic, and what replay does with a bad record.

- **Redis**: the append-only file, `appendfsync` policies, the RDB snapshot,
  `BGREWRITEAOF` and the multi-part AOF (base plus increments, manifest).
  Snapshot-plus-commands is this design's shape.
- **etcd**: the WAL (CRC per record, segment files, repair of a torn tail) and
  snapshots that truncate it. Its retained history serves watches as the
  delta history serves IXFR.
- **BIND**: `.jnl` written before the zone file, `rndc sync`, `freeze`/`thaw`,
  "journal out of sync with zone".
- **Knot**: LMDB journal, `zonefile-load: difference` and
  `difference-no-serial`, `zonefile-sync: -1`, `journal-content: all`.
- **PowerDNS**: the database as the zone; `SOA-EDIT-API`; whether it serves IXFR as a
  primary (recalled as no, unchecked).

Not settled: whether this replaces `persistence.md`'s decision or adds a
fourth trigger to it. Its three triggers (thousands of zones, UPDATE at a
real rate, an external owner of the data) are unmeasured here.
