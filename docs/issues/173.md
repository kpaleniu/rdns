### 173. `rdnsr` answers NXDOMAIN for every RFC 6303 reverse zone, and nothing can override it — **filed 2026-10-05**, **bug**, **ready-for-agent**

`special_names::lookup` answers NXDOMAIN for `10.in-addr.arpa.`, the sixteen
`172.16/12` zones, `168.192.in-addr.arpa.` and the rest of
`PRIVATE_REVERSE_ZONES` (`rdns/src/special_names.rs:97-106`, list at `:150`).
It runs before RPZ and before resolution in both modes
(`rdnsr/src/answer.rs:244`, RPZ at `:263`), and has no flag.

So a PTR for an internal address can never be answered: not by forwarding
(`--upstream` to the server that holds `10.in-addr.arpa.` still gets
NXDOMAIN locally), not by RPZ local data, and not by #172 once it exists.
Every enterprise network with a reverse zone for its RFC 1918 space is
affected.

The comment at `answer.rs:259` places `special_names` before RPZ because "that
table is a protocol requirement rather than a preference". That holds for
`localhost` (RFC 6761 §6.3). Whether it holds for the RFC 6303 zones is the
question to settle when this is taken up: read RFC 6303 on whether these
defaults may be disabled by the operator, and check BIND's
`empty-zones-enable`/`disable-empty-zone` and Unbound's `local-zone: ...
nodefault` for what the others allow. Not checked here.

> *This was generated by AI during triage.*

**Triaged 2026-10-06: bug, ready-for-agent.** Decisions in ADR 0008; terms in
`CONTEXT.md` (**Empty zone**, **Special-use name**).

The question this file left open is settled. RFC 6303 §3: "An
implementation of this recommendation MUST provide a mechanism to disable
this new behaviour, and SHOULD allow this decision on a zone-by-zone basis."
§2 names the sites that need it: those "that make use of delegations for
[RFC1918] addresses … will need to override the default configuration".
BIND has `empty-zones-enable` and `disable-empty-zone`, and creates no empty
zone where one "already exists or is active (covered by a forward-only
forwarding declaration)". Unbound has `local-zone: <name> nodefault` and
`unblock-lan-zones`, and a `stub-zone` does *not* override a default zone —
its manual tells the operator to add `nodefault` as well.

**Category:** bug
**Summary:** let the operator switch empty zones off, singly or all at once;
let a routed domain override one; answer at an empty zone's apex as RFC 6303
§3 says, with AA set.

**Current behavior:** every name under `PRIVATE_REVERSE_ZONES` is answered
NXDOMAIN, AA clear, before RPZ and before resolution, with no flag. The apex
too: `10.in-addr.arpa. SOA` is NXDOMAIN with an SOA for that same name in
the authority section. `127.in-addr.arpa.` has the same apex shape.

**Desired behavior:**

- `--disable-empty-zone NAME`, repeatable, switches one empty zone off;
  `--no-empty-zones` switches all of them off. Config: `disable-empty-zone =
  [...]` and `empty-zones = false` in `[resolver]`. A switched-off zone is
  resolved like any other name (RPZ, caches, recursion or a routed domain).
- Only the RFC 6303 private-address zones are empty zones: RFC 1918,
  `254.169`, `0.in-addr.arpa.`, and the link-local and unique-local `ip6.arpa`
  zones. Special-use names — `localhost.` and its reverse names
  (`127.in-addr.arpa.`, the `::1` reverse), `local.`, `invalid.` — cannot be
  switched off. `::1`'s reverse moves out of the empty-zone list accordingly.
- An empty zone and a routed domain (#172): the more specific name decides,
  a tie goes to the routed domain. A forward zone for `10.in-addr.arpa.`
  overrides it; `--upstream` (a forward zone at `.`) and a routed
  `in-addr.arpa.` do not (ADR 0008). Applies once #172 lands; nothing here
  waits for it.
- At an empty zone's apex, and at `127.in-addr.arpa.`: SOA → the synthetic
  SOA, NS → an NS naming the zone itself (RFC 6303 §3's recommended
  default, which is also the SOA MNAME already written), anything else →
  NODATA with the SOA. Below the apex, NXDOMAIN as now.
- Locally decided answers carry AA=1 (RFC 6303 §3, "return authoritatively
  (AA=1) name errors"). `resolve_validated` clears AA because "this
  resolver is authoritative for nothing"; its comment, or the local path's,
  says why these answers differ: the zones are defined to be empty, so the
  subtree claim RFC 8020 reads into AA is the intended one.
- The comment placing `special_names` before RPZ as "a protocol requirement
  rather than a preference" is corrected in place: true for special-use
  names, not for empty zones. RPZ still runs after an empty zone that is on.
- Refused at startup, naming the entry, before `--check-config` returns
  (§15): a name not in the empty-zone list, with a subzone's message naming
  the empty zone containing it and a special-use name's saying it is fixed;
  `--no-empty-zones` together with `--disable-empty-zone`.
- The startup banner lists empty zones switched off, or "all off", and each
  one a routed domain overrides.

**Key interfaces:**

- `special_names::lookup` gains the configured set, or the set is applied
  around it; the empty-zone list and the special-use names become separate
  tables so the "fixed" half is visible in the type, not in a comment.

- [ ] `--disable-empty-zone 10.in-addr.arpa.`: that PTR is recursed to the

- [ ] Flag and config produce the same set; both together is refused.

**Out of scope:**
