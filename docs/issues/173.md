### 173. `rdnsr` answers NXDOMAIN for every RFC 6303 reverse zone, and nothing can override it — **filed 2026-10-05**, **needs-triage**

`special_names::lookup` answers NXDOMAIN for `10.in-addr.arpa.`, the sixteen
`172.16/12` zones, `168.192.in-addr.arpa.` and the rest of
`PRIVATE_REVERSE_ZONES` (`rdns/src/special_names.rs:97-106`, list at `:150`).
It runs before RPZ and before resolution in both modes
(`rdnsr/src/answer.rs:244`, RPZ at `:263`), and has no flag.

So a PTR for an internal address can never be answered: not by forwarding
(`--upstream` to the server that holds `10.in-addr.arpa.` still gets
NXDOMAIN locally), not by RPZ local data, and not by #172 once it exists.
Every enterprise network with a reverse zone for its RFC 1918 space is
affected.

The comment at `answer.rs:259` places `special_names` before RPZ because "that
table is a protocol requirement rather than a preference". That holds for
`localhost` (RFC 6761 §6.3). Whether it holds for the RFC 6303 zones is the
question to settle when this is taken up: read RFC 6303 on whether these
defaults may be disabled by the operator, and check BIND's
`empty-zones-enable`/`disable-empty-zone` and Unbound's `local-zone: ...
nodefault` for what the others allow. Not checked here.
