**Depends on #172** (stub zones). Nothing here can start before it lands.

**Category:** enhancement
**Summary:** RFC 8806 by composition — `rdnsd` holds the root as a loopback
secondary, `rdnsr` stubs `.` to it — plus the one piece missing: falling back
to the real root servers when the local root cannot be used.

**Why composition and not a mirror zone inside `rdnsr`:** RFC 8806 §3
allows the root service to be "done separately from the operation of the
recursive resolver". `rdnsd`'s secondary already refreshes on SOA timers and
withdraws a zone at EXPIRE, answering REFUSED after it — what §3 asks of
the copy. Rebuilding transfer, refresh and expiry inside the resolver would
be a second copy of that logic (`CLAUDE.md` §7) for a gain §1 itself calls
small: the design "will probably have little effect on getting faster
responses".

**What RFC 8806 requires**, quoted:

- §1: the local root service "MUST be configured to only answer queries
  from resolvers on the same host"; the resolver "validates all responses
  from the root service on the same host, just as it would validate all
  responses from a remote root server".
- §3: "if the contents of the root zone cannot be refreshed before the
  expire time in the SOA, the resolver MUST immediately switch to using
  non-local root servers", and the system "MUST NOT serve stale data for
  the root zone".

**Desired behavior:**

- A stub zone at `.` — and only there — falls back to the root hints when
  its servers cannot be used. No flag: it is §3's MUST. Below the root,
  #172's no-fallback rule is unchanged, because there the fallback leaks
  internal names; at the root those names go to the root anyway.
- Stateful, not per query: the local root is marked down on an unreachable
  server, a REFUSED (what `rdnsd` answers for a withdrawn zone), or an
  answer that fails validation. While down, walks start from the root hints.
  Every 60 seconds an SOA query for `.` is sent to the stub's servers;
  once it is answered and validates, the local root is up again. The
  interval is a constant, not a flag.
- Each transition is logged once, with the reason. A gauge reports whether
  the local root is in use, for §3's "automated method to check that the
  contents of the local root zone are being refreshed".
- A stub zone at `.` with `validate = false` is refused at startup, before
  `--check-config` returns: §1 makes validation a MUST here.
- `docs/spec/05` gains the recipe: `rdnsd --secondary .@<server> --host
  127.0.0.1 --port 5353` and `rdnsr --stub-zone .=127.0.0.1:5353`, citing
  RFC 8806 Appendix B for transfer sources rather than copying addresses
  that go stale. Binding `rdnsd` to loopback is what satisfies §1. Check
  that `--secondary .@…` is accepted for the root before writing it down
  (§4).

**Acceptance criteria:**

- [ ] With a mock local root on loopback and a mock root at the hints: a
      lookup walks from the local root and the hints mock sees nothing.
- [ ] The local root answers REFUSED: the next lookup is answered via the
      hints mock, one transition is logged, the gauge flips.
- [ ] The local root is unreachable: the same.
- [ ] The local root serves a record that fails validation: marked down.
- [ ] Restore it: within one probe interval (paused clock) lookups go local
      again, logged, gauge back.
- [ ] A stub zone at `corp.test.` whose server is down still gives SERVFAIL
      with no query to the hints mock (#172's rule holds below the root).
- [ ] `--stub-zone` at `.` with `validate = false` is refused, also under
      `--check-config`.
- [ ] `cargo test`, `cargo clippy --all-targets`, `cargo doc` clean on
      Windows and Linux, platforms named in the commit.

**Out of scope:**

- A mirror zone fetched by `rdnsr` itself (Unbound `auth-zone`, BIND
  mirror zones).
- ZONEMD (RFC 8976); if wanted it belongs to `rdnsd`'s secondary, for any
  zone.
- Fallback for stub zones below the root.
